## 1. 现状：招聘方侧今天是什么，缺什么

一句话：**招聘方侧已是一条能用的"候选人核验 + 检索 + 投递追踪"链路，但还不是一个能替代招聘系统的 B 端产品。**逐层现状（HEAD 实查 2026-10-07）：

| 层 | 现状 | 出处 |
| --- | --- | --- |
| 招聘方身份 | `accounts.recruiter_declared_at`（迁移 015，F10 落地 09-30）——自声明、可撤销、**无审核、无企业邮箱验证、无组织归属** | PRD §4.4、design-recruiter-roles |
| 人才侧 | `/candidates` 人才检索 + `/recruit` 筛选工作台 + `interviews` 面试计划表 + 面试包导出；候选人规模受**存储层 1000 条扫描窗**限制（`CANDIDATE_SCAN_CAP`，`packages/storage/src/sqlite/profiles-repo.ts:16`：先取最近 1000 条 complete 画像再在内存里精筛）；**翻页已落地**（API `offset`/`limit≤100`，`CandidateWorkspace.tsx:145/501-513` 有上一页/下一页与 `x–y / total`） | handoff T 批次、API.md §3 |
| 投递侧 | `applications` 投递追踪 + outcomeFeedback 结果回写（求职者侧为主） | PRD F11、item61 |
| 数据来源 | 画像库是"被动积累"——只有被分析过的开发者进库，**无主动寻源、无简历导入** | design-c-side-first |
| 商业 | **付费主体在数据模型中尚不存在**（PRD 原文）；#9 未决策 | PRD §3.3 |

### 1.1 五层差距（"完整招聘系统"缺什么）

| 层 | 缺口 | 现状对应 |
| --- | --- | --- |
| ATS 流程层 | **职位发布**、**候选人 pipeline 状态机**（初筛→面试→offer）、**多面试官协作评价**、**结果标签回流** | PRD §4.3/F9+ 仅列方向，未实施；`interviews` 是个人效率工具形态 |
| 身份与组织层 | **teams/memberships/行级归属/多面试官/计费主体** | deferred 挂起，触发条件未到，**触发前不得预建 teams 表**（deferred 原话）；S1 招聘方闸无审核 |
| 人才库规模层 | **存储层 1000 条精筛窗**（`CANDIDATE_SCAN_CAP`；翻页本身已落地）、**主动寻源缺失**、**简历导入建画像**（方案 3 合规红线不做；方案 1 本人上传对账 spike 就绪，但真实样本测量还缺你的 5 份简历） | tools/resume-pdf-spike（合成样本平均抽净率 97.9%）、PRD 数据来源硬边界 |
| 合规与信任层 | **招聘方自声明无审核**、**"谁看了我"告知缺失**、AI 自动化筛选的欧盟高风险义务/个保法说明权 | deferred 合规线、S1 |
| 商业层 | **计费与席位** | #9 未决策、付费主体不存在 |

## 2. 目标与非目标

**目标**：给招聘方一条可付费、可审计、可协作的完整招聘闭环——发布职位 → 从证据级画像库筛选候选人 → 推进 pipeline → 多面试官协作评价 → 结果回流候选人 → 可选告知。同时守住产品护城河（"GitHub/Gitee 行为证据 = 可核验的能力凭证"），不被"帮企业筛人"拖进合规红区。

**非目标（本方案明确不做）**：
- **招聘方代传简历建画像（方案 3）**：第三方 PII、欧盟 AI 高风险用途、境内人力资源服务资质三座山，三者齐备前不得开工（deferred 合规线原话）
- **全自动筛选决策**（无人监督的"帮企业自动筛人"）：触碰个保法自动化决策说明权/拒绝权，不做
- **阶段 3 全自动投递**（C 端，决策 #20 已定不做）
- **C 端功能回退**：单张画像公开只读口径不变（决策 #1-A）

## 3. 分期方案

> 每期自带触发条件与验收标准；**未触发不开工**（对齐 deferred 的"明确触发条件才重启"纪律）。B1 无外部条件、可立即排期；B2 起均有明确的真实需求信号闸。

### B1 人才库价值验证（无外部条件，建议先做）

**目的**：不碰 B 端组织与 ATS，先用数据把"核验价值"做厚，验证招聘方愿不愿意为"可核验画像 + 简历对账"买单。

| 子项 | 内容 | 边界 |
| --- | --- | --- |
| B1-a | **本人上传简历对账**（deferred「简历↔画像对账」方案 1）：上传简历 → 结构化声明抽取 → 与画像输出 `证据支持 / 矛盾 / 无证据` 三态 | **原文不留存**（2026-10-08 接力复跑核实：`tools/resume-pdf-spike` 守卫 **6/6 通过**，含三条"不留存原文"守卫；但**必须先在 spike 目录内独立安装依赖并下载 16.4MB 中文字体**，否则 6 条全红——它是"能强制"，不是"开箱即绿"）；数据主体即本人，合规面与现状同级 |
| B1-b | ~~解除 `/recruit` 前 100 闸：分页化 + 排序~~ **本项前提不成立（2026-10-08 实查）**：翻页与总数展示**已落地**，`limit≤100` 是单页上限不是库上限。真正卡规模的是存储层 `CANDIDATE_SCAN_CAP = 1000`（取最近 1000 条 complete 画像后在内存精筛）——它**不是分页问题**，要把过滤下推回 SQL 才能突破，而那正是当初为规避 SQLite/Postgres 的 JSON 方言差异才躲开的做法。**这个闸今天是否已经 binding 我读不到**：生产画像总数没有免凭证出口（`/candidates` 要招聘方声明），只能由本人跑 `SELECT count(*) FROM profiles WHERE status='complete';` 定；已知的只有"演示预设 3 条"。改为：先量这个数，过了 1000 再立项，且立项内容是"过滤下推 SQL"而不是"加分页" | 只放开检索面，不放开无声明访问（F10 闸保持） |
| B1-c | **人才检索增强**：技能/平台/真实性分级过滤已有；补关键词、导出候选人清单 | 保持只读 |

**前置**：用户提供 **5 份真实脱敏简历**做达标测量（复用 `tools/resume-pdf-spike` 同一脚本）。**达标口径用 spike 自己写死的两条**（`extract.test.js` 守卫 2）：**平均 ≥ 0.95、每份 ≥ 0.90**——合成样本的实测结果是 **平均 97.9% / 最低 93.4%**，那是"已达成的值"，**不能反过来当真实样本的门槛**（真实简历版式更花，只会被更严的线卡住，而那条线没人论证过）。字段抽取另记：合成样本字段命中率 **73.3%**（spike 自陈"玩具级别"，不在达标口径内），B1-a 真要做对账，这块才是工程量所在。
**验收**：① 上传→三态对账→报告展示端到端；② ~~人才库检索可翻页且 >100 条可查~~（**2026-10-08 实查：翻页已在线**，`CandidateWorkspace.tsx` 有上一页/下一页与 `x–y / total`；② 若要做，验收应改成"精筛窗突破 1000 后 `total` 仍正确"）；③ 无任何新表涉及 teams/付费。

### B2 身份与组织第一刀（触发条件未到，不预建）

| 子项 | 内容 | 触发条件 |
| --- | --- | --- |
| B2-a | **S1 审核升级**：招聘方声明加企业邮箱验证或人工审核通道 | 出现 ≥2 个真实外部账号声明招聘方，或冒用身份遍历人才库实例 |
| B2-b | **teams + memberships + 行级归属**（`team_id` 落 `job_postings`/`interviews`/`applications` 关联方）、多面试官 | 二者先到：① ≥2 个真实外部招聘方账号（需共享候选人池/行级可见性）② #9 决策要上 B 端计费（需付费主体与席位）。**触发前不得预建 teams 表** |
| B2-c | **"谁看了我"查看告知**（合规面） | F10 已落地使"招聘方"成为可引用主体，触发条件之一已满足；待重启（B2-a 落地后一并做，因为审核升级后"谁"才可信） |

**边界**：不做席位配额与付费（进 B4）；撤销声明后既有数据不丢（沿 F10 不变式）。

### B3 ATS 流程核心（工程量最大，建议 B2 验证后启动）

| 子项 | 内容 | 边界 |
| --- | --- | --- |
| B3-a | **职位发布**：`job_postings` 扩展发布/下线、`team_id` 归属、招聘方自建 JD | 岗位池（聚合外部源）与自建职位并存，明确来源标识 |
| B3-b | **pipeline 状态机**：`applications` 加 `stage`（new→screening→interview→offer→hired/rejected）+ 事件留痕（对齐 `job_run_events` 只追加惯例） | 状态迁移原子条件更新；候选人可见"到哪一步"（可选开关） |
| B3-c | **多面试官评价**：`interviews` 已有 `created_by_account_id`；补 `interview_feedbacks`（按成员归属、行级可见） | 依赖 B2-b 组织模型 |
| B3-d | **结果标签回流**：面试/offer 结果写回候选人记录，可选告知候选人（联动 B2-c） | 与 C 端 `outcomeFeedback` 同一值域 |

**触发**：B2 组织模型落地且出现真实招聘方付费意向，或单个招聘方要求"完整流程"。
**验收（概要）**：① 招聘方可发布/下线职位且仅团队可见；② 候选人从投递到 offer 全程有可回放的状态流；③ 多面试官各自提交评价、互不可见他人未公开评价；④ 结果回流的"告知候选人"开关默认关（隐私最小化）。

## 6. 合规约束（红线，不随排期放松）

1. **代传简历（方案 3）不做**：同意只能由数据主体给；招聘/筛选在欧盟属 AI 高风险用途（透明度/人类监督/日志/偏差评估）；个保法对自动化决策有说明与拒绝权；境内"帮企业筛人"可能触及人力资源服务经营资质——三者齐备前不得开工（deferred 合规线）
2. **"谁看了我"一旦上线**，"本人同意"从一次性认领变成持续义务，隐私政策与合规口径需同步重写（deferred 原话）
3. **自动化筛选**只做"排序/标签"辅助，最终人决策；任何自动拒绝候选人的规则需人工复核通道
