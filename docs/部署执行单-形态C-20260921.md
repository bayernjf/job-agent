# 形态 C 部署执行单（Vercel + Supabase + Cloudflare）

> 状态：**现行（上线操作序列）**，2026-09-21。本单是 [deployment-runbook-20260920.md](deployment-runbook-20260920.md) §4-C/§10/§11 的**照着勾的操作版**：严格按阶段顺序执行，每步给出「在哪做、复制粘贴什么、看到什么算成功、失败怎么办」。背景与原理查 Runbook，本单不重复。
>
> **责任人标记**：🖥️ = 只能你在网页控制台操作（账单/账号/点击，AI 无法代做）；💻 = 本地终端命令（可让 AI 代跑，涉及连接串/token 时需你提供或自行执行）。
>
> **占位约定**：`<生产域名>` 默认 `app.job-agent.bayjf.com`（Runbook 占位域名，可改；一旦改了，全文所有位置统一替换）。落地页域名 `job-agent.bayjf.com` 不变。
>
> 预计耗时：首次约 60–90 分钟（不含 Vercel Pro 开通审核与 OAuth 应用审核，二者通常即时）。

## 阶段 A：本地前置（💻，10 分钟）

- [ ] **A1. 代码为最新且已构建**
  ```bash
  cd ~/000mycodes/job-agent
  git fetch origin && git switch dev && git pull --rebase
  node -v          # 须与 .nvmrc 一致（Node 24）；不一致先 fnm/nvm use
  pnpm install
  pnpm -r build
  ```
  成功标志：build 全 Done、0 error。

- [ ] **A2. 确认本地迁移 CLI 可用**
  ```bash
  pnpm migrate:status        # SQLite 本地状态能正常打印即可
  ```

- [ ] **A3. 准备一个 GitHub token 供预热/Worker 采集**
  - 生产长期方案建议 GitHub App（Runbook §2-7）；MVP 上线可用一个 classic PAT（仅 `public_repo`/公开只读粒度）作为 `GITHUB_TOKEN`。
  - token 只进 Vercel 环境变量与你本机 shell，**不写入任何文件、不回显到提交**。

## 阶段 B：Supabase 开库（🖥️ + 💻，15 分钟）

- [ ] **B1. 🖥️ 建项目**：Supabase 控制台 New project，区域选**东京（Northeast Asia, Tokyo）**，与 Vercel `hnd1` 对齐；记下数据库密码。
- [ ] **B2. 🖥️ 拿两条连接串**：Project Settings → Database → Connection string：
  - **Transaction pooler（6543）**——给 Vercel 函数，形如
    `postgresql://postgres.[ref]:[password]@aws-0-[region].pooler.supabase.com:6543/postgres?pgbouncer=true&sslmode=require`
  - **Session pooler / 直连（5432）**——给迁移/Actions/CLI 预热。
  - 成功标志：两条串都在手；6543 串含 `pgbouncer=true`。
- [ ] **B3. 💻 本地跑首次迁移（用 5432 串，绝不拿 6543 跑 DDL）**
  ```bash
  DB_DRIVER=postgres \
  DATABASE_URL='postgresql://...5432...?sslmode=require' \
  pnpm migrate:pg:up
  ```
  成功标志：11 个迁移（001–011）全部 applied；再跑 `pnpm migrate:pg:status`（同样带两个环境变量）显示无 pending。
- [ ] **B4. 🖥️ 开备份**：Database → Backups 确认自动备份开启（Pro 计划含 PITR；Free 仅有有限备份，上线前知悉）。

> 失败处理：迁移连不上先查 5432 是否要求 IPv6（Supabase 直连在纯 IPv4 网络可能不通，Session pooler 5432 走 pooler 域名可通）；TLS 报错确认串里带 `sslmode=require`。

## 阶段 E：Vercel 项目（🖥️，20 分钟）

- [ ] **E1. 🖥️ 开通 Pro 计划**：每分钟 cron 是硬前提——Hobby 计划 cron 每天仅 1 次，`* * * * *` 表达式会直接导致部署失败（Runbook §4-C-5，Vercel 计划限制 2026-09 核实）。
- [ ] **E2. 🖥️ Import 仓库**：Add New Project → 选 `bayernjf/job-agent`：
  - **Root Directory = `apps/report`**（`vercel.json` 在此目录）
  - Framework Preset = Astro；Node 版本 24（与 `.nvmrc` 一致）
  - Region = `hnd1`（东京，已在 vercel.json 声明，核对一致即可）
- [ ] **E3. 🖥️ 逐项填 Environment Variables（Production）**，按下表（完整注释以根 `.env.example` 形态 C 段为准）：

| Key | Value |
| --- | --- |
| `DB_DRIVER` | `postgres` |
| `DATABASE_URL` | **6543 Transaction pooler 串**（含 `pgbouncer=true&sslmode=require`） |
| `DB_AUTO_MIGRATE` | `false`（冷启动绝不碰 DDL，迁移只走 B3） |
| `API_MOUNT_PREFIX` | `/api` |
| `TRUST_PROXY` | `true`（反代后才取得到真实 IP 做限流） |
| `GITHUB_TOKEN` | A3 的 token |
| `GITEE_TOKEN` | 可选，仅提额 |
| `GITHUB_OAUTH_CLIENT_ID` / `GITHUB_OAUTH_CLIENT_SECRET` | D1 |
| `GITEE_OAUTH_CLIENT_ID` / `GITEE_OAUTH_CLIENT_SECRET` | D2（不做 Gitee 登录可留空） |
| `AUTH_STATE_SECRET` | C1 |
| `AUTH_CALLBACK_BASE_URL` | `https://<生产域名>`（**不含** `/api`、无尾斜杠） |
| `AUTH_AFTER_LOGIN_URL` | `https://<生产域名>/zh-CN/` |
| `DEMO_IP_SALT` | C1 |
| `CRON_SECRET` | C1 |
| `DEMO_PRESET_LOGINS` | `github:torvalds,github:bayernjf,github:MSNightmare`（默认空，必须显式配；阶段 H 预热） |
| `DEMO_SESSION_TTL_MS` | 留空用默认 `86400000`（24h，2026-09-21 拍板） |
| `PUBLIC_DISPUTE_EMAIL` | 异议受理邮箱（#14 要求上线即有人值守；不配用代码默认值） |
| `LLM_API_KEY` / `LLM_BASE_URL` / `LLM_MODEL` | 可选，不填=纯规则简历 |

  注意：**不设** `PUBLIC_API_BASE`（同域自动回退 `/api`）；**不设** `CORS_ALLOW_ORIGINS`（同域无需 CORS）；东京直连 GitHub/Gitee，**不设** `JOB_HTTP_PROXY`。

- [ ] **E4. 🖥️ 首次 Deploy**，等待构建完成。先不绑域名也可用 `*.vercel.app` 临时地址做 E5。
- [ ] **E5. 💻 用临时地址验证同域转发**（把临时域名代入）：
  ```bash
  ./tools/smoke-deploy.sh https://<project>.vercel.app --cron-secret '<CRON_SECRET>'
  ```
  成功标志：health/页面/cron 401↔200/404/presets 全 PASS（cron 调度器本身在 F 之后验）。
- [ ] **E6. 🖥️ 配置 Cron 真实 token（关键，勿把 secret 提交进 Git）**：
  - `apps/report/vercel.json` 里两条 cron path 当前是 `token=REPLACE_WITH_CRON_SECRET` 占位，**不要把真实 token 替换后提交**（会进入 Git 历史）。
  - 推荐：部署后在 Vercel 项目 **Settings → Cron Jobs** 界面，把两条任务的 path 改为带真实 token：
    - `/api/internal/cron/process-job?token=<CRON_SECRET>`（每分钟）
    - `/api/internal/cron/cleanup?task=all&token=<CRON_SECRET>`（每天 03:17）
  - **部署时实测确认项**：Vercel 控制台对 cron 的手改是否会被后续 git 部署的 vercel.json 覆盖，以平台当期行为为准——每次部署后到 Cron Jobs 面板核对两条 path 仍是真实 token，并在 Runs/Logs 看到 200 而非 401。若确认被覆盖，备选方案见文末「附录 X1」。

## 回滚与故障速查

| 现象 | 先查 | 处置 |
| --- | --- | --- |
| 页面 500 / 函数报错连库 | Vercel logs 是否 6543 串、`pgbouncer=true` | 串错端口/参数是最常见原因；函数只用 6543 |
| 登录回调 404 | OAuth App 回调与 `API_MOUNT_PREFIX` | 回调必须是 `/api/auth/<平台>/callback`，`API_MOUNT_PREFIX=/api` |
| 登录后会话不保 | `AUTH_STATE_SECRET` 是否固定、`TRUST_PROXY` | 多实例必须共享同一 secret；反代后必须 true |
| cron 日志 401 | Cron Jobs 面板 path 里的 token | 与 `CRON_SECRET` 不一致；按 E6/F5 修正 |
| cron 根本不触发 | 计划等级 | Hobby 不支持每分钟，需 Pro |
| demo 限流不生效/IP 全相同 | `TRUST_PROXY`、`DEMO_IP_SALT` | 固定 salt；反代后必须 true |
| 落地页仍是留资模式 | Pages 构建变量后是否 rebuild | 构建期变量，必须重新部署（I2） |
| 迁移在函数冷启动时报错 | `DB_AUTO_MIGRATE` | 必须 false；DDL 只走本地 5432（B3） |
| Actions 岗位同步失败 | secret 用了 6543 | 换 5432 Session 串（G1） |

## 附录 X1：若 Vercel 控制台手改 cron 被后续部署覆盖

两种处置（部署时按平台真实行为二选一）：

1. 每次部署后在 Cron Jobs 面板重新核对/修正 path（运维动作，零代码）。
2. 若平台确以 vercel.json 为唯一事实源、手改必被覆盖，则把真实 `CRON_SECRET` 填入 `apps/report/vercel.json` 两条 path 后单独提交——**须知该 token 因此进入 Git 历史**：它只能触发「认领一个分析任务」与「清理过期数据」，不能读取任何画像/个人数据；上线后应把它视为**低密级调度令牌**，并在轮换流程中接受「轮换需改 vercel.json 并重新部署」。决策前先在 Vercel 当期文档确认 dashboard 编辑的持久化语义。
