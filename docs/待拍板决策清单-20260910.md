## 决策 #1：第一界面优先服务谁（冷启动路径）

**为什么要定**：分析内核 B/C 共用，但"用户第一眼用到的界面"只能先做一个，直接决定开发顺序、冷启动打法与合规路径。

| 选项 | 做法 | 优势 | 代价 / 风险 |
| --- | --- | --- | --- |
| **A. C 端授权为主脊**（助手建议） | 开发者 OAuth 授权本人账号→生成可验证画像→可分享给企业；B 端仅"公开轻预览" | 授权链最干净、合规风险最低；天然 PLG 自传播；积累候选人供给 | 离收费远；早期没岗位可匹配，价值闭环暂不完整 |
| **B. B 端粘贴优先** | HR 粘贴任意公开 GitHub 链接即出完整报告 | 企业更早付费；公开数据无需候选人注册，绕开双边冷启动 | 信任门槛高（要敢据此做雇佣决定）；**未经本人同意对个人打分，合规风险最高** |
| **C. 双界面并行** | 同一内核同时做 B、C 两个入口 | 不押注、覆盖全 | MVP 资源被摊薄，两边都做不深，验证变慢 |

- **助手建议：A**。理由：合规上先拿到"本人同意"，传播上靠开发者分享扩散，且与 #6 的合规默认路径天然一致；B 端用轻预览保留触达，不缺席。
- **影响范围**：PRD 的 F1/F6/F8、冷启动打法、#6 合规路径、落地页主 CTA。
- **不定的后果**：F8（OAuth 认领）放 P0 还是 P1 无法定稿，落地页主按钮指向也无法确定。

> **【你的决定】**
> 选择：**A**（C 端授权为主脊 + B 端轻预览）
> 理由 / 补充：采纳助手建议；授权链干净、合规风险最低、天然 PLG
> 决定日期：2026-09-10

## 决策 #2：真实性结论的呈现形态

**为什么要定**：这是产品口径与信任机制的根基，也直接影响落地页 Hero 里"真实度 98%"示意是否保留。

| 选项 | 做法 | 优势 | 代价 / 风险 |
| --- | --- | --- | --- |
| **A. 分级 + 证据 + 置信区间**（助手建议） | 输出 `likely_authentic / mixed / suspicious / insufficient_data` 四级 + 可点击证据，不显示单一百分比 | 难被反向刷分；误伤可解释、可申诉；合规更稳 | 不如一个分数"直观、好营销"，需要更好的可视化设计 |
| **B. 单一总分（真实度 0–100%）** | 给一个醒目分数 | 直观、转化冲击力强、易传播 | 易被刷分；**误伤真实开发者**；黑箱分数在雇佣场景有歧视/法律风险 |
| **C. 两者并存** | 默认分级，折叠处提供分数 | 兼顾直观与严谨 | 只要对外暴露分数，刷分与误伤风险依旧存在，等于没规避 |

- **助手建议：A**。若市场端确实需要"一眼看懂"，可用**分级徽章 + 一句话结论**替代数字，而不是回到百分比。
- **影响范围**：PRD F3/F7、`Authenticity` 数据结构、落地页 Hero/Moat 文案（需去掉"真实度 98%"或明确标注为示意）。
- **不定的后果**：报告页与落地页的核心展示组件无法开工。

> **【你的决定】**
> 选择：**A**（分级 + 证据 + 置信区间，不显示单一百分比）
> 理由 / 补充：采纳助手建议；难刷分、误伤可申诉、合规稳；落地页"真实度 98%"示意已同步移除
> 决定日期：2026-09-10

## 决策 #15：Chrome 扩展一键填充是否做

**背景**：讨论记录-02 深入分析了投递功能的四种技术路径。Jobright 等竞品的核心载体是 Chrome 扩展（10 万+ 用户，4.6 分），而非后台爬虫。普通填充工具填充的是用户自编简历，我们若做扩展，填充数据来自 GitHub 验证过的可信画像，有本质差异化。

| 选项 | 做法 | 优势 | 代价 / 风险 |
| --- | --- | --- | --- |
| **A. P1 启动 Chrome 扩展 MVP**（助手建议） | P1（画像验证通过后）启动，支持 Workday/Greenhouse/Lever 三大 ATS，填充基础字段（姓名、邮箱、GitHub、技能、教育等），用户主动触发、确认后提交 | 与画像协同最强；差异化明显（"投出 GitHub 验证过的你"）；技术风险低（用户侧扩展，非后台爬虫）；用户感知价值直接 | 需 2-3 周开发；ATS 改版需持续维护；需调整 PRD 非目标 |
| **B. P2 再做** | 等职位聚合+匹配做完后再做扩展 | 不分散 P1 精力 | 错失差异化窗口；用户拿到画像后没有"立刻能用"的投递出口 |
| **C. 永远不做** | 坚持 PRD 原非目标，只做画像，投递完全依赖第三方工具 | 最聚焦 | 产品闭环不完整；用户画像缺少消费出口 |

- **助手建议：A**。理由：Chrome 扩展是投递相关功能里差异化最强、风险最低、与画像协同最好的方向；全自动后台投递才是真正高风险高成本的，扩展不是。差异化卖点"别人填的是你编的简历，我们填的是 GitHub 验证过的你"是别人抄不走的。
- **影响范围**：PRD 第 2.2 节非目标、第 4.2 节 P1 功能列表；需新建 Chrome 扩展工程（可放 apps/extension/）；packages/shared 需预留可导出的画像数据结构。
- **明确不做的边界**：只做"用户主动触发的一键填充"，不做后台全自动投递、不做无人值守批量投递、不存储用户密码。

> **【你的决定】**
> 选择：**A**（P1 启动 Chrome 扩展 MVP）
