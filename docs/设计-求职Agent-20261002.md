# 设计 · 求职 Agent（JobAgent 产品演进构想）

- 状态：**现行（阶段 1「求职工作台」已于 2026-10-03 实施，见 §10；阶段 2/3 待拍板）**——2026-10-02 用户构想落地；落地进度记 handoff
- 定位：把 JobAgent 从「分析工具」升级为「求职 Copilot Agent」——帮用户在**网上找工作**：持续找岗、评估匹配、生成定向简历、投递（人机闸）、跟踪、复盘
- 与既有文档关系：资产盘点以 [技术栈总览-分层架构-20260916.md](技术栈总览-分层架构-20260916.md) 与 [design-targeted-resume-20260915.md](design-targeted-resume-20260915.md) 为事实源；本设计不重复既有实现，只写**增量**

## 0. 一句话

在半自动边界内，让 Agent 闭环完成「找 → 评 → 改 → 投 → 跟 → 复盘」六步求职流程；**投递（真实世界副作用）永远保留用户确认闸**；确定性规则继续负责事实判断，LLM 从「可选润色」升级为「语义理解与决策摘要」，二者分层不混淆。

## 1. 产品定位

| 维度 | 现状 | 构想后 |
| --- | --- | --- |
| 产品角色 | 画像分析工具（求职者自证、招聘方核验） | 求职 Copilot Agent（主动找工作、替用户跑流程） |
| 主动/被动 | 用户发起 → 出画像/简历 | Agent 持续监控岗位 → 主动推荐 → 用户确认 → 执行投递 |
| 自动化边界 | 分析全自动，投递人工 | 分析+准备全自动，**投递半自动（确认闸）** |
| 与 v0.2 流水线 | 无编排 | 正是「轻量串行流水线」的第一落地场景（一个求职任务=多步流水线） |

## 3. Agent 闭环设计（六步）

### 3.1 找（Job Watch）
- **职责**：按用户的「求职偏好」（目标岗位类型、技能组合、地区/远程、公司白名单/黑名单、薪资下限）持续监控岗位源，增量入库 + 打分。
- **现有复用**：job-source 五源适配器、`job_postings` 表、jobs sync 调度。
- **新增**：
  - 扩展采集源：公司 careers 页、Workday 直渲染租户（触发条件＝找到 `data-automation-id` 表单租户）、用户收藏/自选源。
  - 求职偏好模型：`JobPreferences`（Zod 契约，shared），可多套（如「远程全栈」「深圳后端」）。
  - 新岗位事件：Agent 每天/按需扫描增量，产出 `JobWatchItem`（岗位 × 画像 × 偏好 × 匹配分 × 新/变/消失状态）。

### 3.2 评（Match Explain）
- **职责**：每岗给出**可解释匹配报告**——为什么推荐、匹配在哪、缺口在哪、建议补强点。
- **现有复用**：matchScoreTier 确定性打分（title/tags/desc）。
- **新增**：
  - LLM 读 JD 补语义理解（岗位职责/技能/资历要求结构化提取），输出经强约束 prompt + Zod 校验（沿用 llm 包既有模式，fail-closed：无 key 或校验失败 → 纯规则评分降级，不阻塞）。
  - 匹配报告结构：`MatchReport { scoreTier, reasons[], gaps[], suggestedBoost[] }`，gaps 反哺「改」。

### 3.3 改（Tailor）
- **职责**：为选中岗位自动生成**岗位定向简历 + 求职信**。
- **现有复用**：resume-core（rank/tailor/render、no-fabrication）、llm polish（本次开启为「受控润色 + 求职信生成」）。
- **新增**：
  - 求职信生成（cover letter）：基于画像证据 + 岗位缺口 + MatchReport，同样 no-fabrication（只引用画像内事实，LLM 只改写语气与结构）。
  - 产出物管理：每次产出挂 `evidenceRefs` 与来源岗位，本地档案与跨端同步沿用现有 canonical/本地补填机制（design-targeted-resume §5.4.1）。

### 3.4 投（Submit · 人机闸）
- **职责**：用户确认后，扩展自动填充 ATS 表单并提交。
- **现有复用**：扩展 Greenhouse/Lever 填充链路（SW 代发、Shadow DOM 面板、生产域白名单）。
- **新增**：
  - 确认闸：Agent 只能把投递项推到 `awaiting_approval`，**提交动作必须用户点击确认**（面板/报告页「待投清单」一键确认）。
  - 投递意图接口：扩展接收 `SubmitIntent`（岗位 + 简历版本 + 求职信 + 填充映射），确认后执行。
  - 投递限频：单账号每源每日投递上限（默认 20，可配），遵守 ATS/平台反垃圾规则。

### 3.5 跟（Track）
- **职责**：投递后状态追踪、面试安排、提醒。
- **现有复用**：`applications` 表、interviews 管道、面试准备包（interview-kit）、报告页「我的」页。
- **新增**：
  - 状态机驱动的投递时间线（见 §5），状态变化自动通知（站内 + 可选邮件）。
  - 面试提醒：面试前 N 天/小时提醒 + 一键出面试准备包。

### 3.6 复盘（Learn）
- **职责**：投递结果（无回音/被拒/面试/Offer）回写，微调匹配权重与偏好。
- **新增**：
  - 结果反馈表（`application_outcomes` 或扩 `applications` 字段）：结果 → 更新「什么岗位类型命中率高」的画像侧统计。
  - 规则版本化沿用：权重微调进规则版本，可回滚、可审计。
  - 注意：**不做**基于结果的激进自动化（不因几次被拒就大改画像），只做温和统计反馈。

## 4. 设计原则（硬约束）

1. **人机确认闸（最高优先）**：投递 = 真实世界副作用，发出收不回。Agent 只能「准备好」，不能「发出去」。所有对外提交动作必须有用户确认。
2. **证据链不破坏**：Agent 改写的任何产出（简历/求职信）延续 no-fabrication——LLM 只改表达，不引入新事实；每断言挂 evidenceRefs；出口 Schema.parse 双保险。
3. **质量闸防海投**：匹配度低于阈值（scoreTier 阈值，默认「中」以下不投）或缺口过大的岗位不进待投清单，保护用户声誉与产品口碑。
4. **确定性分层**：事实判断（匹配分、真实性、证据引用）永远走规则引擎；LLM 只做语义理解与表达生成，且 fail-closed（无 key/校验失败 → 降级纯规则，不阻塞）。
5. **可解释**：每个「为什么推荐/为什么投/为什么不投」可见可溯源；Agent 每步决策落在状态机与日志，可回放。
6. **合规与限频**：遵守各 ATS/平台投递频率限制；隐私政策同步更新（投递行为数据的使用边界）。

## 5. Agent 编排器（apps/agent）与状态机设计

### 5.1 定位与形态

- 新增 `apps/agent`（独立包，纯函数内核 + 调度壳，对齐现有「内核与 I/O 分离」硬约束）：
  - `agent-core`（纯函数）：求职任务状态机迁移、步骤编排决策、投递意图生成、复盘统计。零 I/O，可夹具测试。
  - 调度壳：由 worker 或独立 cron 驱动（常驻轮询 → Vercel Cron 每分钟认领，沿用现有 analysis_jobs 模式）。
- **与 v0.2 串行流水线的关系**：`JobRun`（求职任务）就是流水线实例——一个任务 = 一串步骤（watch → explain → tailor → submit → track → learn），每步可独立 Profile/规则版本执行。**本设计即轻量串行流水线的首个落地形态**。

### 5.2 状态机（求职任务 JobRun）

```
                    ┌──────────────┐
   创建(偏好/画像)   │   created    │
   ───────────────► │  (草稿,校验)  │
                    └──────┬───────┘
                           │ validate（偏好非空、画像可认领）
                    ┌──────▼───────┐
                    │  configured  │  ← 配置合法，等待首次调度
                    └──────┬───────┘
                           │ start（Agent 开始一轮找/评）
                    ┌──────▼───────┐
   ┌──────────────► │  watching    │  ← 监控岗位源，产出候选
   │                └──────┬───────┘
   │                       │ candidates_ready（候选≥1 且完成评分）
   │                ┌──────▼───────┐
   │                │ recommending │  ← 生成 MatchReport + 定向简历/求职信
   │                └──────┬───────┘
   │                       │ ready_for_approval（≥1 项过质量闸）
   │                ┌──────▼───────────────┐
   │                │ awaiting_approval     │  ← ★ 人机闸：等用户确认
   │                └──────┬───────────────┘
   │                       │ approve / reject
   │                ┌──────▼───────┐        ┌─────────────┐
   │                │  submitting  │───────►│  submitted  │──► tracking
   │                └──────┬───────┘        └─────────────┘
   │                       │ rescan（本轮无合格项 → 回 watching 等下一轮）
   └───────────────────────┘
```

- 状态全集（`JobRunStatus`）：`created → configured → watching → recommending → awaiting_approval → submitting → submitted → tracking → archived`；辅助终态：`cancelled`（用户中止）、`failed`（不可恢复错误，显式标注原因）。
- 关键迁移事件与守卫：

| 事件 | 前置状态 | 守卫/动作 | 后继 |
| --- | --- | --- | --- |
| `validate` | created | 偏好 Zod 校验、画像 claimed 或可匿名 | configured |
| `start` | configured | 生成一轮计划 | watching |
| `candidates_ready` | watching | 候选非空；按 matchScoreTier 过滤质量闸 | recommending |
| `generated` | recommending | 简历/求职信产出成功（Schema.parse 过） | ready→awaiting_approval |
| `approve` | awaiting_approval | 用户确认；限频检查 | submitting |
| `submitted` | submitting | 扩展回执成功，写 applications | tracking |
| `reject` | awaiting_approval | 用户拒绝；记录原因 | watching（等下一轮） |
| `rescan` | watching/recommending | 本轮无合格项 | watching |
| `fail` | 任意非终态 | 显式错误码 + 可重试标记 | failed |
| `cancel` | 任意非终态 | 用户中止 | cancelled |

- 失败与超时策略（沿用 worker 既有模式）：每步重试上限 3、`not_found` 不重试、僵尸任务回收；`failed` 必须有显式原因，**禁止"看似成功"**。
- 投递意图（`SubmitIntent`）单独建模：`{ jobPostingId, resumeSnapshotId, coverLetterId, profileId, sourceFormFields }`——扩展只消费 SubmitIntent，不含 Agent 内部状态。

### 5.3 数据模型增量（草案，双方言迁移，编号续 018+）

| 表/字段 | 说明 |
| --- | --- |
| `job_preferences` | 求职偏好集（多套）：岗位类型/技能/地区/远程/薪资下限/公司白名单黑名单；JSONB + 校验 |
| `job_runs` | 求职任务（状态机实例）：status、profile_id、preference_id、current_step、attempts、last_error、created_at/updated_at |
| `job_run_events` | 状态迁移审计日志（事件、from/to、actor、payload）——可回放 |
| `submit_intents` | 投递意图（人机闸票据）：job_run_id、job_posting_id、resume_snapshot_ref、status（pending/approved/rejected/submitted/failed）、approved_at |
| `applications`（扩展） | 加 `source=agent`、`submit_intent_id`、`outcome_feedback`（结果回写复盘） |
| `resume_snapshots`（如走服务端持久化） | 现有设计决策是「不持久化只存本机」（design-targeted-resume §10），Agent 化后**需重新拍板**：投递审计要求快照可追溯 → 建议按投递意图留存精简快照（对齐 profiles 快照惯例，只存证据指针与精简原始） |

> 迁移规范照 [../MIGRATION_CONVENTION.md](../MIGRATION_CONVENTION.md)：编号 NNN_verb_snake_case.sql、双方言对称、幂等、COMMENT ON。

### 5.4 API 增量（apps/api，登录闸 + 归属校验）

- `POST /agent/preferences`、`GET/PUT/DELETE /agent/preferences/:id`（本人）
- `POST /agent/runs`（创建求职任务）、`GET /agent/runs`（我的任务列表）、`GET /agent/runs/:id`（含当前状态 + 事件流）、`POST /agent/runs/:id/cancel`
- `GET /agent/runs/:id/pending-approvals`（待投清单）、`POST /agent/runs/:id/approve`、`POST /agent/runs/:id/reject`（人机闸两个动作）
- 投递执行由扩展消费 SubmitIntent（保持扩展为执行器，API 只出票据）

## 6. 落地路径（三阶段，每阶段独立可交付）

| 阶段 | 内容 | 自动化 | 外部依赖 | 判据（用户视角） |
| --- | --- | --- | --- | --- |
| **1 · 求职工作台** | 每日汇总匹配岗位 + 自动生成定向简历/求职信 + 待投清单；**人工投递** | Agent 准备、人执行 | 无（纯代码；LLM key 可选） | 「我今天打开页面，10 个匹配岗位 + 简历都备好了，我点开一个个投」 |
| **2 · 半自动投递** | 扩展在确认后自动填充 ATS 并提交 | Agent 准备、人确认、机器执行 | 扩展装好 + 生产 API | 「我在待投清单点『确认』，Greenhouse 表单自动填好，我再点提交」 |
| **3 · 全自动 + 规则边界** | 白名单公司 + 匹配度阈值内 Agent 自主投递（可关） | 预设规则内全自动 | 用户显式授权 + 合规复核 | 「我把 Apple/字节设为白名单，Agent 自主投，每周给我周报」 |

> 建议：先做阶段 1（不碰外部副作用、纯代码可一口气闭环，接上 v0.2 流水线构想）；阶段 2/3 涉及真实投递行为与数据合规，需独立评审与用户拍板。

## 7. 风险与取舍

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| 海投垃圾简历 | 伤用户声誉 + 伤产品口碑 + 可能被 ATS 封号 | 质量闸（匹配阈值）、限频（默认 20/源/日）、白名单模式先行 |
| LLM 引入新事实 | 简历造假嫌疑，砸「可信证据链」招牌 | 延续 no-fabrication 硬约束：LLM 只改表达；出口校验；证据指针必挂 |
| 投递自动化合规 | 各平台条款/反爬/频率限制 | 限频 + 遵守平台规则 + 隐私政策同步更新 |
| 自动化决策不可解释 | 用户不信任 Agent 的推荐/拒绝 | 状态机事件日志可回放；每个推荐带 MatchReport 理由 |
| 自动化 vs 用户掌控 | 用户失去掌控感 | 半自动起步；随时 cancel；所有外部动作确认闸 |
| 复盘反馈污染 | 少数样本导致错误权重 | 温和统计反馈；规则版本化可回滚；样本阈值（如 ≥20 条才生效） |

## 8. 开放问题（待拍板）

> **2026-10-03 更新**：问题 1 已起步（阶段 1 已落地，见 §10）；问题 2/3 被阶段 1 的实现方式绕开（交付物按需重装配、不落库；不接 LLM）；问题 4/5/6 已于 2026-10-03 拍板——**投递＝扩展自动填充、填完等用户点提交**（不得自动点提交）／**复盘＝自动计算 + 人工确认后生效且样本 ≥20**／**对招聘方披露「AI 辅助投递」标识**。权威记录见 [待拍板决策清单 决策 #20](待拍板决策清单-20260910.md)，本节仅保留原始问题清单。

3. **LLM key 策略**：阶段 1 的求职信/JD 理解为可选增强（无 key 降级纯规则）还是必要项（阻塞）——建议可选。

5. **复盘反馈的自动化程度**：权重微调是否自动生效（建议：自动计算 + 人工确认后生效）。
6. **与 B 端（招聘方）的关系**：Agent 投递对招聘方侧是否要披露「AI 代投」标识（合规与透明度）。

## 10. 实施记录 · 阶段 1「求职工作台」（2026-10-03 落地）

阶段 1 的判据（§6）＝「我今天打开页面，10 个匹配岗位 + 简历都备好了，我点开一个个投」。以下只记**与设计原稿的差异与理由**，机制细节以代码与 [API.md](API.md) §3.8 为准。

### 10.1 与设计稿的差异（均为实现期决策，需下一位知悉）

| 设计稿 | 实施 | 理由 |
| --- | --- | --- |
| 新增 `apps/agent`（纯内核 + 调度壳） | 纯内核落 **`packages/agent-core`**；编排壳落 **`apps/api/src/agent-runner.ts`**；调度走 `/internal/cron/agent-tick` | 仓库硬约束是「内核放 packages、I/O 放 apps」；形态 C 没有常驻服务，多一个可部署物只会多一份部署面。阶段 2 若真需要长跑编排，再把 runner 提成 app 也不破坏内核 |
| `JobRunStatus` 含 `submitting`/`submitted` | 取值保留（契约与迁移都留位），阶段 1 **不会进入** `submitting`/`submitted`：`awaiting_approval --submitted--> tracking` | 阶段 1 的「已投」是用户自己投完回填，没有机器投递中间态；预留给阶段 2 的扩展回执 |
| `submit_intents` 存 `resume_snapshot_ref` / `cover_letter_id` | 只存 `profileId` + **岗位精简快照**；简历/求职信**按需重新装配**，不落库 | 直接回应 §8 开放问题 2：画像快照与票据内岗位快照都是不可变事实，重新装配即同一份交付物，因此**不需要**推翻「简历不持久化」的既有决策，快照留存仍可留待阶段 2 拍板 |
| LLM 读 JD 补语义理解（§3.2） | 阶段 1 **不接 LLM**：`MatchReport` 只由确定性规则产出（标题/标签/正文命中 + 岗位标签缺口） | §8 开放问题 3 的「可选增强」立场：无 key 也能完整闭环，先证明规则版可用；`packages/llm` 的 A/B 档模式可原样套到求职信与 JD 理解 |
| 求职信由 LLM 改写表达 | 阶段 1 = **规则版求职信**（`resume-core` 的 `buildCoverLetter`，段落挂 `evidenceRefs`，没证据的段落直接不产） | 同 no-fabrication 与 fail-closed；`COVER_LETTER_RULE_VERSION=0.1` 可复现 |
| 「改」只提到简历 | 另加**导出端点**（`GET /agent/intents/:id/resume`）：服务端按需装配 md/html/json | 扩展/CLI/MCP 等无浏览器场景要拿这份交付物；浏览器端下载仍走 `POST /resumes/build` 以带上本机补填字段（电话/教育不丢） |
| CORS 只允许 GET/POST | 放开为 `GET/POST/PUT/PATCH/DELETE/OPTIONS` | §5.4 的偏好编辑用 PUT/DELETE，而既有 PATCH 端点（投递/面试）本就不在允许列表里，跨域形态 B 一直调不到；一并修正 |
| applications 加 `source=agent` | 加 `applications.submit_intent_id` + `ApplicationOrigin` 增加 `'agent'`（迁移 022） | 既有 `applications.source` 已是"岗位来源"语义（remoteok 等），复用会撞义；仓库里表示"从哪来"的既有列是 `origin`，故扩展它 |

### 10.2 落地产物清单

- **契约**（`packages/shared`）：`JobPreferences`、`JobRun`/`JobRunEvent`、`SubmitIntent`、`MatchReport`（只出 code + 事实）、`CoverLetterDraft`、`AGENT_ERROR_CODES`、请求体 schema。
- **持久化**（`packages/storage` + 迁移 **018–022** 双方言）：`job_preferences` / `job_runs` / `job_run_events` / `submit_intents` + `applications.submit_intent_id`；四个仓储接口与双方言实现（`compareAndSetStatus` 原子条件更新是并发闸）。
- **内核**（`packages/agent-core`，纯函数、零 I/O）：状态机迁移表、偏好→匹配条件与硬过滤、质量闸与候选选择、匹配报告、票据计划、限频判断。
- **交付物**（`packages/resume-core`）：`buildCoverLetter` / `renderCoverLetterMarkdown` / `coverLetterCopy`。
- **编排与 API**（`apps/api`）：`agent-runner.ts`（扫描、装配闸、状态迁移落事件）、`agent-config.ts`（`AGENT_*` 旋钮）、`agent-view.ts`（存储行 → 对外契约投影）、17 条路由（§5.4 全部 + `mark-submitted` + 导出 + cron tick）。
- **界面**（`apps/report`）：`/[locale]/workbench` 工作台页 + `AgentWorkbench` island（偏好 CRUD、任务与事件流、待投清单、匹配报告、确认/拒绝/标记已投/下载交付物）+ 导航入口 + 131 条中英文案。
- **调度**：`/internal/cron/agent-tick`，由 `.github/workflows/cron-poll.yml` 在每次轮询时调用（与 `process-job` 并列），另有「立即扫描」按钮不等 cron。

### 10.3 阶段 2 的接续点（尚未开工）

- `SubmitIntent` 加执行回执（`submitted` 由扩展回写）→ 任务走 `submitting → submitted → tracking`；`applications.origin='agent'` 的既有记录即审计线索。
- 简历/求职信快照留存（§8 问题 2）一旦拍板，落点就是 `submit_intents` 的两列引用 + 精简快照表。
- LLM 语义理解与求职信润色（§8 问题 3）：沿用 `packages/llm` 端口 + `resume-core` 的安全层，默认关闭、fail-closed。
- 复盘回写（§5.3 的 `outcome_feedback`）与权重微调，仍受「样本阈值 + 规则版本化」约束。
