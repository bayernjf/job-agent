- `apps/extension` **没有 `vitest.config.ts`**（`package.json` 里只有 `"test": "vitest run"`），因此吃 vitest 默认的 `testTimeout: 5000`。

**需用户判断的一处张力**：AGENTS.md 记有「仍按 T29 纪律不调 timeout/retries」。但该纪律针对的是**报告页 E2E 用 sleep/retries 掩盖 hydration 竞态**；本例是纯 CPU 型的 jsdom 解析耗时、不涉状态竞态，且仓库已有三个包显式声明 timeout 的先例。故本文按「与兄弟包一致」推荐，但把这条张力明写出来，不默认它可以静默调大。

## 2. P0（三条，均已亲自复核）

### 2.1 分析任务可永久卡死在 `queued`（活性 bug，两个缺陷叠加）

**缺陷 A — `apps/worker/src/index.ts:564`，`makeSources()` 在 try 之外**

```ts
const sources = deps.sources ?? makeSources(deps);   // :564 ← 在 try 之外
try {                                                 // :566
  const result = await processJob(job, repos, sources, logger, usageRecorder);
```

`makeSources`（同文件 `:149-157`）在 `GITHUB_TOKEN` 缺失时**抛异常**。此时任务**已被认领**（`status=running`、`attempts+1`），异常逃出函数，`handleJobFailure` 永远不执行 → **既不置失败也不回队**。

`:561-563` 的意图注释是对的（延迟构造 source，让空队列的 serverless tick 不因缺 token 就 500；常驻 `runWorker` 仍在启动时 fail-fast）——**bug 只在这行落到了 try 外面**。serverless 路径确实不传 `sources`（`apps/api/src/cron-jobs.ts:51-58`），所以这不是理论路径。

**缺陷 B — `reclaimStaleRunning` 不动 `attempts`，且无人把触顶任务置 `failed`**

`packages/storage/src/sqlite/analysis-jobs-repo.ts`：`claimNext` 过滤 `lt(attempts, 3)`（`:56`）并在认领时 `attempts + 1`（`:71`）；而 `reclaimStaleRunning`（`:189-211`）把 `running → queued` 时 set 的字段只有 `status/stage/errorMessage/claimedBy/startedAt/finishedAt/updatedAt`——**完全不动 `attempts`**，也不检查上限。

对照：同文件 `:179-180` 的 `deferToQueued` **是**做补偿的（`attempts: MAX(attempts - 1, 0)`，注释「反复 defer 不耗尽重试预算」）。可见「不烧重试预算」这个意图在 defer 路径上实现了，在 reclaim 路径上漏了。

**没有任何代码路径**把 `attempts>=3 且 status=queued` 的任务置为 `failed`，也没有兜底清扫器（`runMaintenance` 只管 demo/auth，`cron-jobs.ts:77-87`）。

**叠加后的真实场景**：serverless cron 环境缺 `GITHUB_TOKEN` → 认领即抛 → 卡 `running` → 5 分钟后被 reclaim 回 `queued`（attempts 已烧掉）→ 重复 3 次 → **永久不可认领、永不失败**。而 `latestActiveBySubject` 仍会返回它，前端轮询永不收敛，用户看到「任务一直转圈」。

**附带**：`MAX_RETRIES` 只在 `handleJobFailure`（`worker:456`）生效，两侧仓储把 `3` 写死（sqlite `:56` / postgres `:53`），所以这个旋钮调到 >3 会被静默截断，并直接喂给缺陷 B。

**修法**：① 把 `:564` 移进 try（或单独包一层，失败走 `handleJobFailure`）；② `reclaimStaleRunning` 在 attempts 触顶时落 `failed`（或加一条清扫器把 `queued && attempts>=3` 置失败）；③ 让仓储的 `3` 读 `MAX_RETRIES`，消除双事实源。

**证据等级**：[CODE-LEVEL]（逐行读过双方言实现与调用点；未在生产复现）

### 2.2 扩展 Bearer token 明文入库，且被列表接口原样回显

`apps/api/src/routes/auth.ts:294-301`：

```ts

  id: apiToken,                    // ← id 列存的就是明文 token
```

认证路径**是正确的**哈希查找（`apps/api/src/principal.ts:138`：`apiTokens.getActiveByHash(sha256Hex(bearer), now())`），所以 `token_hash` 不是摆设——**但明文就存在它旁边，哈希带来的保护被完全抵消**。任何库读取、`tools/backup-db.sh` 的 pg_dump 产物、或被记录的响应体，都能拿到有效的 90 天滑动 token（`API_TOKEN_TTL_MS` + `touchAndSlide`）。

更直接的是 `GET /auth/extension-tokens`（`auth.ts:312-327`）：

```ts

id: t.id,                        // ← 完整明文
fingerprint: t.id.slice(-4),     // ← 从明文切出来的"指纹"
```

**证据等级**：[CODE-LEVEL]（读了 create / list / delete 三个端点与仓储接口 `packages/storage/src/repositories/api-tokens.ts:8-20`）

### 2.3 BYOK `baseUrl` 的 SSRF 面：注释承诺的校验根本不存在

`packages/shared/src/index.ts:2073-2076`：

```ts
export const UserLlmConfigSchema = z.object({
  provider: z.string().min(1).default('custom'),
  baseUrl: z.string().url(), // https 校验由 API 层 refine（SSRF 面）
  model: z.string().min(1),
});
```

把该文件里**每一条** `refine`/`superRefine` 都列出来核对了：`:1364`、`:1394`、`:1521`、`:1542`、`:1615`、`:1996`、`:2113`、`:2368`——**没有一条校验 baseUrl 的 scheme 或主机**。`:2113` 那条只管「给了 apiKey 就必须同时给 baseUrl+model」。另一处 schema `:2109` 同样只有 `z.string().url().optional()`。

再查 API 层：`apps/api/src/routes/llm.ts:214-233` 把用户传的 `typed.baseUrl` 原样交给 client（`:216` 表单模式、`:221` 已存模式），`llm-resolve.ts:39-49` 每次 polish/cover-letter 调用复用同一 URL。**全链无 scheme/主机校验。**

于是任何已登录用户都能把它指向 `169.254.169.254`（云元数据）、`127.0.0.1:5432`（生产 PG）、`[::1]` 等。

**必须说清的一个细节**：允许 `http://localhost:11434/v1` 是**刻意设计**——`packages/llm/src/openai-compatible-client.ts:43` 的文档字符串明写「含版本前缀的根地址，如 `https://api.openai.com/v1` 或 `http://localhost:11434/v1`」，为的是支持自建/Ollama 网关。所以修法**不是**「强制 https」，而是屏蔽 loopback / link-local / 私网 / 元数据段（或走 allowlist）——这正是那条缺失的 refine 该做的事。

**响应体回显**：`openai-compatible-client.ts:201-213` 把非 2xx 响应体前 300 字符（经 `redactSecret` 脱敏 key，S5）放进抛出的 message。SSRF 本身已 [CODE-LEVEL] 确认；**这段 message 是否真到达 HTTP 响应体未完整追到底，标 [INFERRED]**——若到达（子代理指向 `llm.ts:248` 与 `resumes.ts:318` 的 `reason: err.message`），就成了有限的内网读取原语，严重度从 blind SSRF 升级。

**另**：`POST /account/llm-config/validate` 只有 `requireUser` 闸、**无限频**，构成端口扫描原语。

**修法**：给 `UserLlmConfigSchema.baseUrl` 补真正的 refine（拒 loopback/link-local/私网/元数据；解析主机名后判 IP 段，注意 DNS rebinding 需在 connect 时再校验或禁跟随重定向）；validate 端点加限频；把 `:2075` 的注释改成与代码一致。

**证据等级**：SSRF 面 [CODE-LEVEL]；响应体到达 HTTP 响应 [INFERRED]

### 3.2 `search_runs` 可永久卡 `running`

## 4. 结构性工程债（5 条）

### 4.1 全仓没有 linter，13 条 `eslint-disable` 是死注释

## 5. 经全面检查确认**干净**的面

这部分同样重要——核过且没问题，避免下一位重复劳动：

- **招聘方私有 JD 硬不变量成立**：四个池读取（`search` 默认 / `countBySource` / `countActiveFresh` / `markStale`）在**双方言**都排除了 recruiter 行（sqlite `job-postings-repo.ts:117-121`/`:175`/`:188`/`:206`；postgres `:191-192`/`:244`/`:256`/`:273`）。`listBySearchRun` 安全是因为 `insertOwned` 把 `searchRunId` 写死为 null（sqlite `:241`）。未过滤的 `getById` 在每个调用点都做了归属校验 → 404（`job-postings.ts:193-198`；`recruiting.ts:161`/`:313`/`:373`/`:406`）。**这是全项目最难的不变量，它守住了。**
