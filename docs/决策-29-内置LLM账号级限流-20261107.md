## 1. 问题与风险

决策 #21-3 拍板「内置模型＝平台承担、免费」，并同时承诺「**账号级限流兜底**」；
但该兜底在代码里从未实现。当前暴露面如下（2026-11-07 代码实查，非推测）：

| 端点 | 代码位置 | 现状 | 风险 |
| --- | --- | --- | --- |
| `POST /resumes/cover-letter` | `apps/api/src/routes/resumes.ts:196` | 只校验 `principal.kind === 'user'`，随后 `resolveTextLlm` 直接取内置 provider | 任意登录用户可无限生成求职信 |
| `POST /resumes/build`（`polish: true`） | `apps/api/src/routes/resumes.ts:109` | 登录态检查在 `:48`，无任何账号配额 | 无限润色 |
| `GET /agent/intents/:id/cover-letter?polish=llm` | `apps/api/src/routes/agent.ts:687` | 仅校验 intent 归属，LLM 分支无配额 | 通过工作台入口无限调用 |

放大因素：

- **hub 模式「分配即授权」**（`apps/api/src/routes/llm-resolve.ts:71-83`）：只要 model-hub
  投影里存在文本模型，**任何登录用户**都自动获得内置 provider，`ADMIN_ACCOUNT_LOGINS`
  白名单在 hub 模式下不再生效。
- **注册无门槛**：GitHub OAuth 账号可自由创建，单账号限流失效时账单暴露面等于「互联网规模」。
- 反向代理 / IP 漂移使既有 demo IP 桶无法约束登录用户（同一账号换 IP 即可绕过）。

结论：决策 #21-3 承诺的兜底缺失，属于**账单风险**，不是体验优化。

## 2. 边界

1. **只对 `source === 'builtin'` 计数**：`resolveTextLlm` 的返回值是唯一事实源；
   `source === 'byok'` 与 `'none'` 一律不计数、不检查（决策 #21-4：BYOK 不吃平台配额）。
2. **不改变 demo / IP 各桶语义**：`session`、`analyze`、`match`、`subject`、`removal`、
   `candidates`、`funnel`、`llm-validate` 的窗口、阈值、响应保持不变；本决策只新增一个
   独立 `kind`。
3. **不计 cron 侧内置调用**：`AGENT_JD_LLM_ENABLED` 的 JD 抽取由后台 cron 以服务端 env
   凭证执行（`apps/api/src/index.ts:213-236`），没有登录账号上下文，不属本限流对象；
   它已有的墙钟预算（`AGENT_JD_LLM_BUDGET_MS`）继续作为其成本闸。
4. **不改变失败语义**：润色仍然「LLM 失败/校验失败 → 规则版」，但**配额拒绝是显式 429**，
   不静默降级（否则用户无法知道是配额而不是模型故障）。

## 3. 计数主体

- 主体＝**登录账号**：`principal.kind === 'user'` 时的 `principal.accountId`（`acc-<uuid>`），
  不混入 IP、demo session 或扩展 token。
- 与 IP 的关系：限流键不含 IP，因此换网络、换设备、浏览器 Cookie 与扩展 Bearer token
  都命中同一账号桶；这正是「账号级」的含义。
- 与 demo session 的关系：demo/anonymous 无法解析出内置 provider（`resolveTextLlm`
  只在 `kind === 'user'` 分支返回 builtin），因此不参与账号桶；demo 仍由其既有
  IP/会话配额约束。
- 多账号轮换（批量注册）不在本层解决：本决策只保证单账号成本有上限；跨账号防刷属于
  注册风控/运营问题，记录为残余风险。

## 4. 存储

**复用 `demo_rate_events` 滑窗表，不新增迁移。**

- 写入：`kind = 'llm-account'`；`ip_hash` 列存账号 id（该列是 `TEXT NOT NULL`，
  只承担「不透明键」职责；账号 id 本身不含 PII）。与 IP 哈希（64 位 hex）在形态上
  天然可区分（账号 id 带 `acc-` 前缀）。
- 隔离：所有查询都带 `kind`，与既有桶互不影响；`kind` 在 DB 层无 CHECK 约束
  （`db/migrations/sqlite/007_create_demo_rate_events.sql`），只在
  `packages/shared/src/index.ts` 的 `DEMO_RATE_KINDS` 联合类型里登记新值。
- 索引：`idx_demo_rate_events_ip_kind_created (ip_hash, kind, created_at)` 正好覆盖
  `WHERE ip_hash=? AND kind=? AND created_at > cutoff`，无需新增索引。
- 清理：`cron-jobs.ts` 的 `purgeRateEventsBefore` 保留 24h，账号事件不会无限增长；
  1 小时窗口的查询也不会被历史数据拖慢。
- 并发：沿用 demo 的「先 count 后 insert」两段式，**不做事务/唯一约束**。两个并发请求
  在阈值边缘可能都通过，超额上界＝并发数（与既有 `llm-validate` 桶同口径）。
  收紧到严格上限需要唯一约束或 `SERIALIZABLE`，成本与收益不匹配。

## 5. 参数

| 变量 | 默认 | 口径 |
| --- | --- | --- |
| `LLM_ACCOUNT_RATE_PER_HOUR` | `20` | 单账号、单桶、1 小时滑动窗口内的**内置 LLM 调用次数**上限 |

- **取值依据**：正常求职者一天产出数份定向简历，每份最多一次润色 + 一次求职信；
  20/h 远高于正常节奏，同时把单账号最坏账单压到「20 次调用/小时」。
- **调参方式**：只改 env，不改代码；非法值（非整数、< 1）回退默认并 warn，与
  `demo-config.ts` 的 `positiveInt` 同纪律。
- **是否区分端点**：**不区分**。求职信与润色共用 `llm-account` 桶。理由：两者单价同级，
  分桶会让「换端点继续用」成为绕过路径；单桶也更便于向用户解释。
- 计数时机：解析出 builtin 之后、真正发起 LLM 请求之前。失败的上游调用也计数——
  超时/5xx 同样可能产生上游计费，且可防止「失败重试」刷配额。

## 6. 失败策略

**DB 不可用时 fail-closed。**

- 理由：本限流存在的目的就是控制账单；DB 读失败时若 fail-open，故障窗口内正好是
  无限消耗窗口。另一方面，DB 故障时 `resolveTextLlm` 之前的登录/画像读取多数也已失败，
  fail-closed 对可用性的边际损失很小。
- 实现：配额检查抛错不静默放行；服务端记录
  `[llm] account quota check failed, failing closed`（含 `describeError`），
  对外返回 `503`、`code: 'LLM_QUOTA_UNAVAILABLE'`。
- 审计发现：该 503 与错误日志是唯一信号；`/health?deep=1` 已覆盖 DB 往返，
  运维可据此关联。若长期出现该码，说明配额表/连接池需要扩容，而不是放宽限流。

## 7. 响应契约

超限：

```
HTTP/1.1 429 Too Many Requests
Retry-After: 3600
Content-Type: application/json

{
  "error": "builtin LLM account rate limit exceeded",
  "code": "LLM_ACCOUNT_RATE_LIMITED",
  "limitPerHour": 20,
  "retryAfterSeconds": 3600
}
```

- 状态码：`429`；`Retry-After` 头与 body 的 `retryAfterSeconds` 同为 `3600`
  （窗口为滑动 1 小时，保守取整小时）。
- **不返回剩余额度**：剩余额度需要额外读取并暴露消耗进度；客户端只需知道
  「被限、何时可重试」。
- 前端呈现：
  - 报告页求职信错误框按 `code` 显示专属文案（新增 `coverLetterRateLimited`），
    提示「内置模型本小时额度已用完，可稍后重试或在设置里配置自己的模型 Key」；
  - 简历润色/下载走通用失败态（现有 UI 无 per-code 分支），文案层后续可扩展；
  - 前端不自动重试，避免 429 叠加。

## 9. 残余风险

- 多账号轮换：单账号限流无法约束批量注册，需注册风控或设备指纹，另行决策。
- 并发边缘超额：见 §4，上界为并发请求数。
- 账号 id 作为限流键写入 `demo_rate_events.ip_hash`：列名语义偏窄，但无 CHECK/FK，
  读取方只按 `kind` 区分；若将来做通用限流表，应改名或加 `subject_kind` 列（新迁移）。
- 计数发生在调用前：上游明确拒绝（4xx 非账单）的请求也会占 1 次配额；当前选择是
  「宁可少给一次，也不打开失败重试刷额度的口子」。
