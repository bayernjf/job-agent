## 五、本机环境已知问题（2026-09-22 新发现，非代码缺陷）

- **现象**：storage 包 `postgres-behavior.test.ts` 本机 7 例 PG 行为测试全部 skip，且 afterAll hook 超时（60s，Vitest 默认）。
- **根因**（已探针定位）：embedded-postgres 18.1.0-beta.15 内置的 PG 18.1 二进制在本机 macOS 上启动即 FATAL：`postmaster became multithreaded during startup / HINT: Set the LC_ALL environment variable`。已排除 LC_ALL（设置后仍复现）、Node spawn 因素（bash 直接启动同样 FATAL）→ **macOS 系统级兼容问题**（系统版本升级后 postmaster 多线程检测误报）。embedded-postgres 的 `start()` 在该失败路径 `reject(undefined)`，测试代码 `(err as Error).message` 因此抛出 TypeError 掩盖真实错误，且 afterAll 的 `storage?.close()`/`embedded?.stop()` 卡满 60s。
- **影响**：仅影响本机本地跑 storage 的 7 例 PG 测试；CI（Linux runner + Docker `postgres:16-alpine` service + `DATABASE_TEST_URL`）不受影响；Windows 克隆 2026-09-21 实测 embedded PG 7/7 通过（item43）→ 确为 macOS 本机环境问题。
- **建议**（不阻塞评审结论，落地时择一）：
  1. 升级 `embedded-postgres` 到含 macOS 修复的版本（锁文件变更，需全量回归）；
  2. 本机跑 storage 测试时设置 `DATABASE_TEST_URL` 用 Docker PG（`docker compose --profile with-pg`）；
  3. 修复测试自身对非 Error reject 的健壮性（`catch (err) { unavailable = err instanceof Error ? err.message : String(err) }`）并给 afterAll 加超时——该改动属测试基础设施，可在部署批次外另行原子提交。

> **2026-09-22 补记（T2 闭环）**：建议 3 已落地（`describeError` 兜底非 Error reject、`withTimeout` 启动/teardown 限时、`embeddedRunning` 标志使启动失败不再调 `stop()`、afterAll 整体限时 30s）；建议 2 已实测——用 Docker `postgres:16-alpine`（宿主端口 5434，避让本机已占用的 5432）设 `DATABASE_TEST_URL` 跑 postgres-behavior **7/7 全绿**；同日 macOS embedded PG 复跑亦冷启动成功 **7/7**（initialise 3.1s / start 3.5s），表明上方 FATAL 为**间歇性**环境状态而非稳定缺陷，且健壮性修复保证其复现时安全 skip、不再挂死 hook。详见 handoff item47。
