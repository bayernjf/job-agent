## 总结论：当前未达到"核心完全可用、可上线"的 MVP，但差距集中、无需重做

代码功能完成度约 90%，核心分析链路真实跑通；但有 **3 个 P0 阻塞**：1 个代码漏接线（直接打断"可复核"核心承诺）、1 个 P0 明确要求的入口缺失、1 个生产环境从未部署。前两个修复量都很小（预计半天内），第三个主要是按 Runbook 做控制台操作（需要凭证/域名/账单）。

## P0-1 证据实体永不落库（代码漏接线）

采集层产出 `collected.evidence[]`（含 URL/claim），但 worker 成功分支只写 profiles 快照，全文无 evidence 字样、从不调 `importFromProfile`；该写入方法全仓生产代码零调用。实测真实作业 profiles=1、evidence=0。

影响：核验视图原始外链、面试准备包、在线简历证据回溯全部静默拿空。768 个单测未抓到——夹具 evidence 恒为空且无落库断言。

修复量：小（worker 成功分支补一次 `importFromProfile` + 补非空证据落库断言）。

## P0-2 异议入口未渲染

i18n 字典有孤立 key `report.dispute="提交异议"`，但报告页/布局/组件无任何引用，也无 mailto/表单。PRD F6.4 验收明确「P0 先留表单/邮件入口」。

修复量：极小（报告页局限区加一个 mailto 链接，补中英 key 对齐测试）。

## P0-3 生产从未部署

Runbook §11 控制台清单全部未做：Supabase 建库 + 5432 首迁移、Vercel 项目/env/Pro（每分钟 cron 硬前提）、域名 DNS、生产 GitHub/Gitee OAuth App、CRON/AUTH/SALT secrets、Actions DATABASE_URL。线上落地页实测仍留资模式，US-1 线上不成立。

性质：部署操作而非开发，多数步骤需账号授权；代码侧已就绪。

## 到达可上线 MVP 的路径（建议顺序）

1. 修 P0-1：worker 接 evidence 落库 + 测试断言
2. 修 P0-2：报告页异议 mailto 入口
3. 拍板合规/配额：#14 留存删除策略 + demo 配额 TTL
4. 形态 C 部署：按 Runbook 控制台操作

## 关键发现说明（最重要的一个）

**P0-1 是典型的"测试全绿但核心价值断裂"**，证据链四方闭合：

1. 采集层确实产出证据实体：`packages/github-source/src/types.ts:19` 定义 `evidence: EvidenceItem[]`
2. worker 从不消费：`apps/worker/src/index.ts` 全文（除注释）无 `evidence` 字样，`processJob` 只取 `collected.input` / `collected.meta`
3. 写库方法无人调用：`evidence.importFromProfile` 在 sqlite/postgres 双实现都有，但全仓生产代码零调用
4. 实测真实作业：`profiles=1、analysis_jobs=1、evidence=0`
5. 读侧有多个消费者会拿到空数组：报告页 `loadEvidence`（`apps/report/src/lib/db.ts`）、面试准备包（渲染 `(no clickable source evidence)`）、API `/resumes/build`

产品的核心差异化是"**可信、可解释、可复核**"——分析结论本身正确，但招聘方在报告页点不到任何一条原始 commit/PR 链接，这个承诺在线上形态不成立。修复只是 worker 成功分支补一次批量写入 + 一条非空断言测试。
