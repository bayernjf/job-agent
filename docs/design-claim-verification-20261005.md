# 逐条声明核验设计草案（简历声明 ↔ 画像证据）

> **状态：待拍板，未实施。** 本文只做设计与取舍，不含代码；任何一条被批准前不得开工。
> **提出时间**：2026-10-05。**提出场景**：上线评估时发现"改"这一步与产品主张（可信、可解释、**可复核**）之间缺一个反向通路。
> **关联**：[PRD](PRD.md) 的 F4/F5/F6、[design-targeted-resume](design-targeted-resume-20260915.md)（正向：画像→简历）、[市场与竞品更新-20261003](市场与竞品更新-20261003.md)（DINQ 等"行为证据"玩家）、[待拍板决策清单](待拍板决策清单-20260910.md)（本文 §9 的五个问题进这张表）。

---

## 1. 问题

今天产品只做**正向**：`packages/resume-core` 从画像里挑证据、排岗位、生成简历（`docs/design-targeted-resume-20260915.md`，硬约束是"只重排不造事实"）。

缺**反向**：拿到一份简历（招聘方手里那份，或求职者自己写的那份），逐条问"这句话，GitHub 行为痕迹支撑得起吗"。这个问题：

- 是招聘方真实的第一动作——他们看的从来不是画像，是简历；
- 是产品差异化的正面——竞品（DINQ 等）在做"多源画像"，把简历与行为痕迹**对账并给出可复核判定**这件事没人做；
- 是我们自己话术的承诺——「每条结论绑定证据、可点击回溯」如果没有反向通路，只是"我们生成的东西可回溯"，不是"你带来的东西可核验"。

现有零件：`spike` 已做过合成 PDF 抽文本（`tools/resume-pdf-spike/`，handoff item109），但**没有任何上传/解析进入 `apps/api` 或 `apps/report`**，也没有判定模型。

## 2. 判据（硬约束，不可谈判项）

1. **无证据不下结论**；证据不足输出 `insufficient_data`，不许把"没查到"写成"造假"。
2. **三态判定优先于分数**：`supportable` / `partial` / `no_trace`（+ `insufficient_data`）。分数会被读成"造假概率"，那是产品明确拒绝过的方向（真实性分级只做保守判定，见 PRD F3）。
3. **不动画像可复现性**：核验是画像之**上**的一层，绝不回写 `AbilityProfile`，绝不升 `RULE_VERSION`（同一版本对应两套输出＝缓存与分享链接失去可复现性）。
4. **LLM 只能在辅助位**：若用 LLM 拆句子，输出必须过 Zod，且**判定结论只能由纯函数规则给出**；LLM 不可用时功能整体降级为手填，不返回猜测。
5. 中英双语同步落地（决策 #4），内核写英文数据层、渲染侧走 composer 现拼（AGENTS「内核散文的语言归属」三条硬规矩直接适用）。
6. 隐私：声明文本是**用户带来的第三方信息**，默认不公开；谁能读必须逐条写死（§6）。

## 3. 三条路与其真实代价

| 方案 | 形态 | 优点 | 风险 |
|---|---|---|---|
| **A. 简历文件解析** | 上传 PDF/DOCX → 抽条目 → 逐条对账 | 招聘方零输入，体验最顺 | 解析质量不可控：错切一句 = 错判一条；把解析噪声引进判定路径，与判据 1 冲突。spike 只证明了"能抽出字"，没证明"能可靠切条" |
| **B. 结构化声明输入** | 求职者/招聘方逐条填"我做过 X（含仓库/PR/时间）" | 输入边界清晰，判定可解释可复核；无解析风险 | 要求人填，摩擦高；填的内容本身可能编造（但这正是核验要处理的） |
| **C. 只标注画像自身** | 招聘方对画像 `skillTags[].evidenceRefs` 点"有/弱/无痕迹" | 最便宜，纯 UI | **答不了 §1 的问题**——它核验的是我们生成的东西，不是对方带来的东西 |

**推荐：B 为主干，A 降级成 B 的导入器。** 即：判定的输入永远是**一条条结构化声明**（人或解析器给都行，但落到同一张表、同一套规则）；PDF 抽取只用于**预填输入框**，抽取失败或置信不足时退回手填，**永不直接进入判定**。这样 A 的价值（省人力）保住、风险（污染结论）卸掉。C 不做（它给的信任增量近零）。

## 4. 数据模型草案（迁移 029–030，双方言，命名对齐 `MIGRATION_CONVENTION.md`）

```
claim_verifications
  id                    TEXT PK
  profile_id            TEXT      NULL   -- 绑到某张画像快照（不绑=纯声明，待人工分配）
  subject_platform      TEXT
  subject_login         TEXT
  claim_text            TEXT      NOT NULL      -- 数据层原文（英文优先）
  claim_source          TEXT      NOT NULL      -- manual | resume_import（A 的产物标这个）
  claim_ref             TEXT      NULL          -- 来自导入时的页/条目定位，仅供复核
  verdict               TEXT      NOT NULL      -- supportable | partial | no_trace | insufficient_data
  matched_evidence_refs TEXT      NOT NULL      -- JSON 数组；no_trace 时为 []
  confidence            REAL      NULL          -- 规则算出的支撑强度，非"造假概率"
  verifier_account_id   TEXT      NULL          -- 谁触发的核验（声明式身份，不新建角色体系）
  rule_version          TEXT      NOT NULL      -- 本层独立版本，见 §5
  created_at / updated_at
```

外加 `claim_import_batches`（可选，仅在 A 落地时需要）：存导入原件的**哈希与条目数**，**不存原件全文与文件**（隐私与留存承诺一致，见隐私政策"不收集/不留存"口径）。

## 5. 判定内核放哪，规则怎么算

- **位置**：新建 `packages/claim-core`（纯函数、无 I/O，与 `analyzer-core`/`resume-core` 同构）。放 `resume-core` 里会被它的"只重排不造事实"语义污染；放 `analyzer-core` 会牵动画像版本，违反判据 3。
- **独立版本** `CLAIM_RULE_VERSION`，与 `RULE_VERSION` 完全解耦。
- 规则草案（每条都是"取不到的事实不许编"）：
  1. 声明里的显式仓库/PR/issue 指针 → 直接查 `evidence`（`url`/`rawRef` 命中）→ `supportable`。
  2. 否则按技能词典（`packages/shared` 单一事实源）抽 token → 在 `skillTags` / commit 主题 / PR 标题里找共现 → 命中且证据条数 ≥N → `supportable`；命中但条数不足或只落在自建仓库 → `partial`。
  3. 抽不出可核验 token（如"优秀的沟通能力"）→ **`insufficient_data`，绝不判 `no_trace`**。
  4. `no_trace` 只在"有明确可核验 token 且画像里确凿没有"时给出，且文案必须写"本工具未观察到"，不写"没做过"。
- 输出**只给 code + facts**，句子由渲染侧按 locale 现拼（判据 5）。

## 6. API 与鉴权（逐条写死，不留模糊）

| 端点 | 身份 | 说明 |
|---|---|---|
| `POST /profiles/:id/claim-verifications` | `user` 且为画像本人，或已声明招聘方 | 建声明并触发核验；未认领画像只允许招聘方建（核验公开画像） |
| `GET /profiles/:id/claim-verifications` | 同上（**首版不向 anonymous 开放**，见 §9 ⑤ 已定；表原拟"未认领画像对 anonymous 公开"延后） | 将来若要公开，口径与 `/job-recommendations` 的匹配理由证据一致（决策 #10 要求可回溯）；认领画像只本人/招聘方可读全量 |
| `DELETE /claim-verifications/:id` | 创建者本人或画像本人 | 声明是可撤回的用户输入，不进快照 |
| `POST /claim-verifications/import`（**仅 A 获批后**） | `user` | 只回条目草稿，不回判定 |

> **路径命名（2026-10-05 定）**：原草案写的是 `/profiles/:id/claims`，与既有 `POST /profiles/:id/claim`（**认领**画像，非本功能）只差一个复数 s，语义却完全不同，误打错字会安静写进错的表。故改为与表名 `claim_verifications` 同名的自解释路径。**既有 `/claim` 端点不动**。

绝不放进 `/exportable` 投影，绝不进 MCP 面（服务账号不是人，给密钥也不解锁这类内容——`docs/design-mcp-surface-20260928.md` 三条硬原则沿用）。

## 7. 表面

- **B 端**：报告页 `?view=recruiter` 增加"声明核验"区块（与现有三处证据外链同一屏）；招聘工作台 `/recruit` 列表加"已核验条数"计数。
- **C 端**：工作台加"自检"入口——投递前先看自己简历哪几条没痕迹。这条把产品从"被核验"变成"先自查"，是 C 端优先定位下的主要价值。

## 8. 验收（缺一条就不算落地）

1. 每条判定都能点开 `matched_evidence_refs` 的原始记录（复用现有 `evidence` 读取闸口径）。
2. 反证：把规则里的证据查询摘掉，`supportable` 用例必须转红——不许出现"恒判 supportable"的绿灯。
3. `insufficient_data` 路径有真实夹具用例（抽象能力类声明），且输出文案不得出现"造假/没做过"。
4. 画像快照逐字节不变：同一输入在落地前后 `AbilityProfile` 与 `RULE_VERSION` 完全一致（这条用测试钉，不靠口头承诺）。
5. 真进程 smoke：起构建产物 + 一次性库，跑一次端到端建声明→读判定，不依赖 mock。

## 9. 待拍板（进决策清单，我给建议但不替你定）

1. **是否只做 B**（我的建议：是；A 之后作为导入器单独再议）。
2. **未认领画像的核验结果是否公开**（建议：公开条数与三态分布，不公开声明原文；理由与风险见 §6 隐私行）。
3. **`no_trace` 的对外措辞**（建议固定为"本工具未观察到对应痕迹"，并在报告页注明采集窗口 `dataWindow`——窗口外的贡献本来就不在数据里）。
4. **是否允许求职者隐藏某条核验结果**（建议：允许隐藏自己的、禁止隐藏招聘方对公开画像发起的核验；否则可复核性被单边作废）。
5. **`CLAIM_RULE_VERSION` 首版是否随 MVP 对外**（建议：先只对已声明招聘方与本人开放，样本与误判率看过一轮再公开化）。

## 10. 明确不做

- 不做"简历打分/ATS 排名"（与真实性核验是两个产品）。
- 不做 DOCX/图片 OCR 与任意格式解析（判据 1 的延伸：解析器越弱，判定越脏）。
- 不把核验结果写回画像快照、不作为真实性分级的输入。
- 不在本刀引入 LLM 判定路径（LLM 只做 §3 的可选预填，且默认关闭，沿用 `packages/llm` 现有的 fail-closed 形态）。
