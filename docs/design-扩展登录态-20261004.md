# 设计：扩展登录态（API Token + 一次性授权码）

> 状态：现行 · 2026-10-04
> 关联：求职 Agent 阶段 2 A2（[设计-求职Agent-20261002.md](设计-求职Agent-20261002.md) §10.4）；决策 #22 登记于 [待拍板决策清单-20260910.md](待拍板决策清单-20260910.md)
> 原则对齐：AGENTS.md（主链 user principal 鉴权）、S7/S8 扩展安全审计、auth_sessions 既有模式

## 1. 背景与目标

求职 Agent 阶段 2（半自动投递）A2＝扩展消费 `submit_intents` 自动填充岗位表单。`submit_intents` 归属登录账号（`account_id`），API 写操作（approve/reject/mark-submitted）要求 `user` 级 principal（否则 401）。**但扩展当前完全匿名只读**：content script 经 SW relay 只调公开只读接口（by-subject / exportable / analyze），无任何身份凭证。

目标：让扩展获得**登录用户身份**，能调用 agent 写接口；同时不破坏既有安全边界（决策 #15：不做后台自动投递、不存密码）。

## 2. 为什么不能直接复用 Cookie

API 的用户鉴权靠 HttpOnly Cookie `jobagent_session`（同域、SameSite）。扩展 content script 运行在 ATS 页面（greenhouse.io / lever.co / myworkdayjobs.com），其 fetch 由 SW 以**扩展源**发起，到 API（生产 `app.job-agent.bayjf.com`）属第三方上下文；现代浏览器第三方 Cookie 限制（SameSite=Lax/Strict、Storage Partitioning）使 Cookie 无法可靠送达。因此扩展需独立的**持票凭证**：`Authorization: Bearer <api_token>`。

## 3. 方案选型

| 方案 | 说明 | 结论 |
| --- | --- | --- |
| A. 扩展直接带 Cookie | 第三方 Cookie 被拦，不可靠 | 弃 |
| B. 扩展内嵌完整 OAuth | GitHub/Gitee redirect_uri 需支持 `chrome-extension://` 域，改动大、跨域回调复杂 | 弃 |
| C. **工作台签发一次性授权码 → 扩展兑换 API Token**（本设计） | 复用工作台既有 OAuth 登录；扩展只拿 code→token；token 长期、可撤销、哈希存储 | **采纳** |

C 的核心理由：登录动作留在已登录的工作台（app 域），扩展不重做 OAuth；code 短时效、单次消费、经 `externally_connectable` + S7 origin 校验的通道传输；token 可撤销，风险可控。

## 4. 端到端流程

```
用户（工作台已 OAuth 登录）
  │ 1. 工作台「扩展授权」页点击授权
  │    POST /auth/extension-token/issue   (cookie user session)
  │    服务端：生成一次性授权码 ext-code（TTL 5min，绑定账号，单次消费）
  ▼
工作台页面
  │ 2. chrome.runtime.sendMessage(EXTENSION_ID, {type:'jobagent.authCode', code})
  │    （externally_connectable 白名单 + SW 侧 S7 origin 校验，fail closed）
  ▼
扩展 background（SW）
  │ 3. POST /auth/extension-token/consume  {code}   →  {apiToken}
  │    服务端：校验 code 未消费未过期 → 标记 used → 签发 api_token（tkn-<32B>）
  │            仅此一次明文返回；库中只存 SHA-256 哈希
  │ 4. 存 chrome.storage.local（key: apiToken + 账号信息）
  ▼
扩展 SW 代发请求
  │ 5. relay 时从 storage 读 token，注入 Authorization: Bearer <tkn-...>
  │    命中 user principal → 可调 /agent/intents/* 等 user 级接口
  ▼
撤销路径
  │ 工作台「扩展授权」列表（尾 4 位指纹 + 创建/最后使用时间）
  │ DELETE /auth/extension-tokens/:id  → revoked_at 置值即失效
```

## 5. 数据模型（迁移 026）

`extension_auth_codes`（一次性码）：
- `id` TEXT PK（`ext-code-<32B>`，明文即凭证，一次性）
- `account_id` TEXT NOT NULL（绑定签发账号）
- `expires_at` TEXT NOT NULL（签发 + 5min）
- `used_at` TEXT NULL（消费时刻；非 NULL 即已消费）
- `created_at` TEXT NOT NULL

`api_tokens`（长期令牌）：
- `id` TEXT PK（`tkn-<32B>`，仅签发时明文返回一次）
- `account_id` TEXT NOT NULL
- `token_hash` TEXT NOT NULL UNIQUE（SHA-256 hex；**服务端不存明文**）
- `name` TEXT NOT NULL（默认「浏览器扩展」）
- `expires_at` TEXT NOT NULL（90 天，滑动续期：命中后顺延）
- `last_seen_at` TEXT NOT NULL
- `revoked_at` TEXT NULL
- `created_at` TEXT NOT NULL
- 索引：`(account_id)` 供授权管理列表；`token_hash` 唯一索引供鉴权查找

与 `auth_sessions` 的区别：session 主键即明文 cookie 值（HttpOnly 保护），token 走 Authorization 头每请求可见，故**只存哈希**、主键独立。

## 6. API 契约（docs/API.md §3.10 增量）

| 端点 | 鉴权 | 说明 |
| --- | --- | --- |
| `POST /auth/extension-token/issue` | cookie user | 签发一次性 code；响应 `{code, expiresAt}`。code 只经工作台→扩展通道传输 |
| `POST /auth/extension-token/consume` | 无（code 即凭证） | `{code}` → `{apiToken, name, expiresAt, account:{platform,login}}`；code 单次消费，重复/过期 410 |
| `GET /auth/extension-tokens` | cookie user | 授权管理列表：`[{id, name, fingerprint(尾4), createdAt, lastSeenAt, expiresAt}]` |
| `DELETE /auth/extension-tokens/:id` | cookie user（仅本人） | 撤销：`revoked_at` 置值；已撤销幂等 204 |

Principal 中间件扩展（index.ts）：`Authorization: Bearer <tkn->` 且**不等于 CRON_SECRET**（短路）→ `token_hash=SHA256(bearer)` 查 api_tokens（active 且未过期且未撤销）→ user principal（`kind:'user', accountId, sessionId:'token:'+id`）；滑动续期 `last_seen_at`/`expires_at`。命中 token 时跳过 cookie 解析。

## 7. 安全设计

- **不存明文 token**：库中只有 SHA-256 哈希；明文仅签发响应返回一次。
- **code 单次消费 + 5min TTL**：consume 原子地「查→校验→置 used→签发」（SQLite 事务/单行 UPDATE 条件判断，防重放）。
- **传输通道**：工作台→扩展仅经 `chrome.runtime.sendMessage`（externally_connectable 白名单 + SW 侧 `isAllowedExternalOrigin` fail closed）；content script 永不接触 code/token。
- **注入点唯一**：token 只在 SW relay（`relayApiRequest`）注入，目标 host 仍过 S8 `isAllowedRelayHost` 白名单；content/panel 拿不到 token。
- **撤销即失效**：`revoked_at` 非 NULL 即匿名；工作台列表仅展示指纹（尾 4 位），不可逆查明文。
- **滑动续期**：命中 token 时顺延 `expires_at`（上限 90 天），长期不用自动过期，配合撤销构成完整生命周期。

## 8. 扩展侧实现点

- `background/index.ts`：`onMessageExternal` 增加 `EXT_MSG_AUTH_CODE` 分支（先过 S7）→ consume → 存 `chrome.storage.local`。
- `lib/sw-relay.ts`：`relayApiRequest` 注入 Authorization（读 storage 的 token；无 token 不带头，保持匿名兼容）。
- `lib/api.ts`：新增 `getAuthStatus()`（向 SW 查询 token/账号，供面板显示「已连接 / 未连接」）。
- 面板：未连接显示引导文案 + 链接到工作台授权页；已连接显示账号登录名。
- `manifest`：无需新增权限（`storage` 已有；host_permissions 已含 API 域）。

## 9. 边界与不做项（MVP）

- 不做 token scope 细分：token 权限与登录用户一致（与 cookie session 同权）。
- 不做扩展内 OAuth：登录始终发生在工作台。
- 不做自动投递：A2 填完停手、等用户点提交（决策 #20 边界不变）。
