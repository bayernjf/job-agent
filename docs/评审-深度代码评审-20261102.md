## 3. 逐条发现

### P1-1 融合画像认领口径允许跨平台冒名，且认领无冲突检查

**位置**：
- `apps/api/src/routes/profiles.ts:143-146`（claim）、`:190-193`（unclaim）、`:255-258`（DELETE 归属判定）
- `apps/api/src/routes/claim-verifications.ts:80-84`（authorizeVerifier）、`:209-212`（DELETE 归属判定）
- `packages/storage/src/sqlite/profiles-repo.ts:100-106` 与 `packages/storage/src/postgres/profiles-repo.ts:89-94`（`markClaimed` 无条件 UPDATE）
- `packages/storage/src/sqlite/accounts-repo.ts:82-91`（`setClaimedProfile` 不排斥第二账号）

**事实链**（全部实读确认）：
1. 融合画像（`subjectPlatform='all'`）的归属判定为 `profile.subjectLogin === principal.login`，**不比对 `principal.platform`**；注释自陈"任一源命中即可认领"。
2. `markClaimed` 是无条件 `UPDATE ... SET subject_claimed=true`，claim 端点也没有"该画像是否已被其他账号认领"的检查——已被认领的画像可被第二个账号再次 claim，两个账号的 `claimed_profile_id` 可同时指向同一画像（归属判定全部基于 login，双方都会通过）。
3. 认领者可调 `DELETE /profiles/:id`（`profiles.ts:228-273`），级联删除 evidence/applications/interviews 与画像本体；也可撤回任意 claim-verification（`claim-verifications.ts:193-221` 的 `isProfileOwner` 分支）。
4. 融合画像任何身份都能触发生成（`POST /analyze` demo 配额 3 次/24h/IP，配额权重 2），`platform=all` 的融合假设是"同 login 即同一人"。

**攻击路径**：受害者 GitHub login `X` 存在融合画像（攻击者可自行触发分析生成）→ 攻击者在 Gitee 注册/持有同名 login `X` → Gitee OAuth 登录 → `POST /profiles/:id/claim` 通过（'all' 分支不校验平台）→ `DELETE /profiles/:id` 删除受害者画像全部数据；或对招聘方场景冒名"本人"。

**影响**：他人画像数据被冒名销毁（evidence/applications/interviews 级联删除）、身份冒用（本产品卖点即"可信"，本人认领标记是信任锚点）。触发条件需要目标有融合画像 + 攻击者持有另一平台同名 login，可能性中低，但破坏性是 P1 级。

**修复建议**：
- `claim` 的 'all' 分支校验 `principal.platform` 与画像主源平台一致（融合画像主体标识落库时即定主源，见 `claim-verifications.ts:150-152` 的"融合主源 GitHub"口径）；
- `markClaimed` 改为条件更新（`WHERE subject_claimed=false`），已被认领返回 409，认领被抢需先 unclaim；
- 在 `docs/deferred-items.md` 安全线登记该口径的复核决策（当前登记表无此条，已核对）。

### P3-1 CORS 配置 `allowHeaders` 未含 `Authorization`

**位置**：`apps/api/src/index.ts:148-149`。
**事实**：`allowHeaders: ['Content-Type']`；扩展 Bearer token 场景不受影响（MV3 `host_permissions` 绕过 CORS），默认 `*` 模式也不发凭证。但配置了 `CORS_ALLOW_ORIGINS`（形态 B 跨子域浏览器直连）后，浏览器跨域请求带 `Authorization` 头的预检会 403——求职偏好 PUT/DELETE、投递 PATCH 已特意放开方法（`:146-148` 注释），头部却没收口。
**影响**：未来若有浏览器端跨域 Bearer 调用会踩坑；当前无实际利用面。
**修复建议**：`allowHeaders: ['Content-Type', 'Authorization']`。

### P3-2 邮件 digest 目的地址未经验证

**位置**：`apps/api/src/routes/notifications.ts:76-115`（`PUT /agent/notifications/email-digest`）。
**事实**：登录用户可把任意邮箱登记为自己的 digest 目的地址，无验证邮件确认环节。`docs/deferred-items.md:50` 已登记"给其他登录用户发信需要 Workers Paid + 目的地址验证流程"，但那是**计费维度**的登记；从**滥用面**看，当前即可被用来向任意第三方邮箱发送本站 digest 邮件（轻量骚扰/信誉通道滥用），发送内容为本人求职 digest，危害低。
**修复建议**：登记目的邮箱时发一次性验证链接，验证通过前不产信；或至少在 deferred 条目中把"未验证可发信"标注为已知滥用面。

### P3-3 评审/审计文档行号基准会静默腐烂

**位置**：`docs/评审-全面代码审查-20261024.md` 自述"行号基准 SHA `642576a`、冻结不回改"（做法正确）；本次评审中发现其 §6 部分建议动作与现状已不完全对应（如 `shared/src/index.ts` 现为 1903 行，文中记 1890——属正常的后续演进）。
