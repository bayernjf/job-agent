## 1. 产品方向回顾（对齐基础认知）

### 1.1 一句话定位

AI 时代，以 GitHub 为"可验证工作证据"的招聘（B）+ 应聘（C）双向闭环平台。

### 1.2 核心洞察

- AI 让传统招聘链路失真：简历可批量生成/造假、关键词筛选筛的是"文案能力"、面试可被八股训练
- GitHub 留下的是**行为痕迹**（commit 演进、PR 协作、Issue 讨论、被他人 merge 的代码），是"做过的事"而非"说过的话"
- 但 GitHub 本身也被 AI 污染（模板仓库、刷 star、灌水 commit），所以**护城河不是"看 GitHub"，而是"鉴别真实性 + 深度分析"**

### 1.3 功能分层（PRD 已定义）

| 阶段 | 核心功能 |
|------|---------|
| **P0（MVP，当前）** | 公开 GitHub 用户名 → L0+L1 采集 → 真实性分级 + 能力标签 + 真实项目面试题 → 报告只读分享 → 落地页 demo 接真 → 海内外同步（中英双语） |
| **P1** | 本人 OAuth 认领 + 完整报告 + 改进建议；招聘方公开轻预览；Gitee 首个并行证据源；L3 语义层；异议/申诉入口 |
| **P2** | 岗位发布、画像 vs 岗位匹配排序、一键投递、面试结果标签回流、订阅/付费 |
| **P3** | L2 clone 静态分析（隔离沙箱）、L4 跨库聚合、非技术岗多元证据源 |

### 1.4 是否只局限于 GitHub？

**不是。GitHub 只是第一个证据源，MVP 先拿它跑通内核。**

- 架构上是 `EvidenceSource` 抽象，分析内核与证据源解耦，新增证据源不改内核
- 数据模型已预留多源：`EvidenceItem.sourcePlatform` 类型为 `'github' | 'gitee' | 'portfolio' | string`
- Gitee 已排到 P1（决策 #4 修订为"海内外同步"后从 P3 提前）
- 远期支持作品集、案例、证书等多元证据源（非技术岗）

## 2. Jobright 深度竞品分析

### 2.1 产品画像（基于公开信息，2026-09 核实）

| 维度 | 数据 |
|------|------|
| 推出时间 | 2025 年推出 Jobright Agent（自动投递代理） |
| 规模 | 月访问量 ~520 万，Chrome 扩展 10 万+ 用户，评分 4.6/5 |
| 职位库 | 800 万职位，日增 40 万+ |
| 核心功能 | AI 职位匹配、简历定制、浏览器扩展一键填充、自动投递（Orion AI）、内推人脉、H1B 筛选、申请追踪 |
| 覆盖平台 | Workday、Greenhouse、Lever、Taleo、iCIMS 等主流 ATS 系统 |
| 投递模式 | supervised（用户确认每步）+ autopilot（全自动），宣传"90% 自动化" |
| 商业模式 | Freemium，付费版月费约 $20–50 |

### 2.2 Jobright 成功的 6 个原因

#### 原因 1：海外 ATS 高度标准化——基础设施级红利

海外招聘市场有一个中国没有的特点：**ATS（招聘管理系统）高度集中且标准化**。

- 大公司几乎都用 Workday、Greenhouse、Lever、Taleo、iCIMS 中的一个
- 这些 ATS 的表单结构、字段命名、投递流程是统一的——适配一次 Workday，几千家用 Workday 的公司都能用
- 类似"电商都用 Shopify"，做一个 Shopify 自动下单工具就能覆盖几十万商家

**对比国内**：Boss直聘、拉勾、猎聘、智联、51job 各搞各的，没有统一 ATS 标准，公司官网五花八门。国内做自动投递的适配成本是海外的 5–10 倍。

#### 原因 2：产品策略——浏览器扩展为主，不是纯后台爬虫

Jobright 的核心载体是 **Chrome 扩展**（10 万+ 用户，4.6 分），不是后台无人值守爬虫。

关键优势：
- **用用户自己的浏览器和 IP**：不存在 IP 封禁问题，投递行为看起来就是真人操作
- **用用户自己的登录态**：不需要管理账号池/Cookie，用户在哪个网站登录了，扩展就能用
- **用户主动触发**：用户在目标页面点一下扩展按钮才填充，不是后台偷偷投——合规风险大幅降低
- **反爬检测难**：在真实浏览器里、真实用户 IP、真实登录态下操作，平台很难区分是人手还是扩展

纯后台爬虫（无头浏览器）是辅助和高端功能，不是主力。

#### 原因 3：法律环境——海外对浏览器扩展容忍度更高

- 美国 CFAA 主要打击"未经授权访问系统"，但用户在自己的浏览器里、用自己的账号、主动触发扩展操作，法理上属于"用户授权的代理行为"，风险较低
- Chrome 扩展商店本身就允许表单填充类工具（密码管理器、购物助手都是同类）
- 招聘平台 ToS 虽然禁止自动化，但执法成本高、且针对的是大规模后台爬虫，对用户侧扩展通常睁一只眼闭一只眼
- 海外用户对"用工具提升效率"的接受度高，不觉得这是作弊

#### 原因 4：时机——2024–2025 年 AI 求职赛道爆发

- 2024 年起美国科技行业裁员潮+招聘放缓，求职者竞争加剧，"投得更快更多"的需求刚性化
- LLM 成熟让"职位描述→定制简历"的质量达到可用水平
- LoopCV/Sonara 等前辈验证了付费意愿（月费 $20–50），Jobright 不需要教育市场
- 2025 年推出 Agent 功能时，赛道已经热了但还没有绝对垄断者

#### 原因 5：差异化功能——H1B 筛选 + 内推人脉

Jobright 不是只靠"自动填充"，有两个差异化功能带来口碑传播：

- **H1B 签证担保筛选**：整合政府公开的 H1B 披露数据，只显示会担保签证的职位。对海外求职者（尤其是印度/中国工程师）是刚需，成为早期口碑点
- **Insider Connections（内推人脉）**：识别目标公司里的校友/前同事，给冷触达模板

共同特点：**用公开权威数据做出别的工具没有的功能**，不是在"填充速度"上内卷。

#### 原因 6：商业模式验证——Freemium + 高客单价

- 免费版：职位匹配 + 有限填充
- 付费版：月费约 $20–50，解锁无限填充、自动投递、简历定制
- 目标用户是正在找工作的专业人士，找到工作后就不用了——但找工作期间愿意为"省时间+多机会"付费
- 520 万月访问 × 假设 3–5% 付费转化 × $30/月 = 月收入数百万美元量级

### 2.3 Jobright 的"两种爬虫"——纠正认知偏差

用户听说"Jobright 也有爬虫"，这是事实，但需要区分两种完全不同的"爬虫"：

| 维度 | 第一种：职位聚合爬虫 | 第二种：投递自动化 |
|------|-------------------|-------------------|
| **用途** | 建立 800 万职位库，从各来源抓公开职位列表 | autopilot 模式下后台自动填表单、提交投递 |
| **技术** | 轻量爬虫 + 公开 API + RSS，抓职位列表页 | 无头浏览器（Playwright/Puppeteer 类），模拟用户操作 |
| **是否主力** | ✅ 是，核心基础设施 | ❌ 不是，辅助功能，实际效果参差不齐 |
| **法律风险** | 低——抓公开信息，hiQ v. LinkedIn 判例支持 | 高——模拟用户投递，违反多数平台 ToS |
| **维护成本** | 中——职位列表页结构相对稳定 | 高——表单经常改版，验证码、账号封禁是无底洞 |
| **实际效果** | 稳定，800 万职位库可持续运营 | 多个第三方评测指出"execution mixed"（实际效果参差不齐），经常卡在验证码/复杂表单 |

**关键结论**：Jobright 有爬虫，但爬虫主要用来**抓职位**（建库），不是用来**投简历**（投递主力是用户侧的浏览器扩展）。这两件事的技术难度、法律风险、维护成本完全不在一个量级。

### 2.4 Jobright 与 JobAgent 的区别与相似

| 维度 | Jobright（AI 求职助手） | JobAgent（可信画像） |
|------|------------------------|---------------------|
| **证据来源** | 用户自述简历 + AI 改写/生成 | GitHub 行为痕迹（commit/PR/Issue/被 merge 的代码），每条结论可回溯 |
| **核心痛点** | 解决"投得更快"——自动化投递、表单填充、简历定制 | 解决"信不信"——真实性验证 + 可复核能力证据 |
| **信任问题** | 结构性缺陷：AI 简历幻觉（Reddit 大量用户报告被插入不存在的技能/虚构指标），简历真假既无法验证也不负责验证 | 定位就是解决信任：四级真实性分级 + 证据引用 + insufficient_data 兜底 + 异议申诉通道 |
| **产品形态** | 求职效率工具（C 端为主，帮求职者更快投出更多简历） | 可信能力画像（B/C 双向：C 端看自己在招聘方眼中的样子+改进建议；B 端核验候选人真实水平+生成基于真实项目的面试题） |
| **护城河** | 自动化流程、职位库规模、浏览器扩展粘性 | 真实性验证引擎、行为深度分析（时序模式、外部贡献、项目演进）、结果标签回流的数据壁垒 |
| **与竞品关系** | 与 LoopCV/Simplify 正面竞争（都在做求职自动化） | 互补而非正面竞争：明确不做自动投递/表单填充/内推自动化，把画像做成"消费端"，求职者可携带可信画像去增强申请说服力，未来可与这类平台互操作 |

**一句话总结区别**：
> Jobright 帮你"更快地投出简历"，JobAgent 帮招聘方"看清简历背后的真实能力"——前者优化投递效率，后者解决信任验证，是互补关系而非替代关系。

## 3. 投递功能技术路径分析

如果要做"更快地投递出简历"相关功能，有四种技术路径，差异极大：

| 路径 | 原理 | 代表产品 | 合规性 | 工程量 | 适合我们吗 |
|------|------|----------|--------|--------|-----------|
| **① 浏览器扩展自动填充** | 扩展注入 JS，识别页面表单字段，一键填充简历信息 | Simplify（十万级安装）、LazyApply、Jobright 扩展 | 较高（用户主动触发，在用户自己的浏览器里） | 中 | ✅ 推荐，P1 可启动 |
| **② 无头浏览器自动化（RPA）** | Playwright/Puppeteer 模拟用户操作：登录→搜索→填表单→点投递 | LoopCV 部分功能、Sonara | 中低（模拟真人操作，但违反多数平台 ToS） | 大 | ❌ 不推荐做主力 |
| **③ 平台 API 对接** | 招聘平台开放的 API（LinkedIn Easy Apply API、Greenhouse、Lever 等 ATS 系统） | 企业级招聘工具 | 高（官方授权） | 小（但覆盖平台有限） | ⚠️ P2 可考虑，覆盖有限 |
| **④ 爬虫聚合 + 半自动投递** | 爬虫抓职位列表→结构化→用户在我们平台确认→跳转到原平台投递（带预填充） | 多数求职聚合站 | 中（抓公开职位信息风险较低，投递仍在原平台） | 中 | ✅ P2 可做职位聚合部分 |

### 3.1 各路径技术难点

#### 路径②（无头浏览器自动化）的难点（最大，为什么不推荐做主力）

1. **反爬虫/反自动化机制**：
   - 验证码（reCAPTCHA v3、hCaptcha、滑块、图形验证码）——全自动场景下极难绕过
   - 行为检测（无头浏览器有特征指纹，平台可检测并封禁）
   - IP 封禁（批量投递必然触发频率限制，需要代理 IP 池，住宅代理成本高）
   - 账号封禁（投递账号被封是常态，需要账号池+养号策略）

2. **平台适配成本**：
   - 每个招聘平台的表单结构、投递流程、字段命名都不一样
   - 平台经常改版（季度级甚至月度级），每次改版都要重新适配——持续运维成本，不是一次性开发
   - 国内平台（Boss直聘等）反爬尤其激进，且 App 端为主，Web 端功能受限

3. **登录态与账号管理**：Cookie/Session 过期、2FA 无法自动化、多账号切换

4. **法律合规风险**：几乎所有招聘平台的 ToS 都禁止自动化投递/爬虫；美国 CFAA、欧盟 GDPR、国内《网络安全法》《数据安全法》都有相关约束；已有先例（LinkedIn 起诉过自动化工具，国内 Boss直聘也起诉过爬虫公司）

### 3.2 全自动后台投递——明确不做的决策

**全自动后台投递（无人值守、批量、后台爬虫）在可预见的未来都不是产品方向。**

这不是"技术上做不到"，而是产品定位上刻意不做：

1. **我们的护城河是"可信"，不是"投递效率"**——投递效率是可以被抄的功能，可信画像是需要长期积累的数据壁垒
2. **Jobright/LoopCV/Simplify 已经把投递效率做成熟了**——正面竞争没有胜算，互补合作才有空间
3. **全自动后台投递的法律风险和维护成本极高**——账号封禁、平台起诉、反爬对抗是无底洞
4. **用户真正的痛点不是"投得不够多"，而是"投了没人信"**——AI 简历洪水下，招聘方需要的是可信验证

**PRD 第 2.2 节「非目标」原文**：
> 不做自动投递、ATS 表单自动填充、内推自动化（这些是效率工具主场，JobAgent 定位为可被其携带/互操作的"可信画像消费端"）

> 注意：PRD 当前把"ATS 表单自动填充"也列在非目标里。如果要做 Chrome 扩展一键填充，需要调整这个决策——见第 5 节。

## 4. 职位聚合爬虫可行性分析

### 4.1 结论

**可以做，而且是路线图里 P2 就规划了的功能。** 这不是"要不要做"的问题，是"什么时候做"的问题。

PRD 第 4.3 节 P2 明确写了：
> P2：岗位发布、画像 vs 岗位匹配排序、一键投递、面试结果标签回流、订阅/增值付费。

职位聚合是"岗位发布/匹配"的基础设施——没有职位库，匹配和投递都无从谈起。所以它是 P2 的前置依赖，必然要做，只是当前 MVP 阶段不做。

### 4.2 技术路径

| 环节 | 方案 | 难度 |
|------|------|------|
| **数据源** | 公开 API + 轻量爬虫 + RSS | 低 |
| **抓取范围** | 先聚焦技术岗（Wellfound、YC Jobs、GitHub Jobs 替代品、Stack Overflow Jobs 等） | 低 |
| **去重与清洗** | 按公司+职位标题+地点哈希去重，LLM 提取结构化字段 | 中 |
| **存储与更新** | Postgres 存职位，定时增量抓取（每日/每小时） | 低 |
| **搜索与匹配** | 全文搜索（Postgres full-text / Meilisearch）+ 技能标签匹配 | 中 |

**整体评估**：一个熟练工程师 2–4 周可以出 MVP 版本（覆盖 3–5 个主流技术岗职位源，日更，基础搜索）。

### 4.3 法律风险：很低，但有边界

- 抓公开职位列表：海外 hiQ v. LinkedIn 判例确立了"公开数据可爬"的原则，风险很低
- 不抓用户隐私数据：只抓职位本身（标题、公司、地点、要求），不抓求职者个人信息
- 遵守 robots.txt 和频率限制：不暴力爬，设置合理间隔，用缓存
- 国内数据源需谨慎：Boss直聘等国内平台反爬激进且有诉讼先例，海外数据源优先

### 4.4 为什么现在不做（MVP 阶段优先级判断）

不是不能做，是现在做性价比不高：

1. **当前核心假设还没验证**：MVP 的目标是验证"单账号 GitHub 深度分析报告"本身是否有区分度、可行动。如果画像本身不被用户认可，职位库再大也没用
2. **职位聚合是"有了画像之后才需要"的功能**：用户先需要知道"我长什么样"（画像），然后才需要"我适合投什么"（职位匹配）。顺序不能反
3. **资源有限**：当前是单人开发，同时铺画像内核 + 职位聚合会两边都做不深
4. **职位库是规模效应**：100 个职位和 10 万个职位对早期用户体验差异不大，但维护成本差 100 倍。等有用户量了再扩规模更合理

### 4.5 建议

**按原计划 P2 再做**，但现在可以做两件低成本的准备：

1. **数据模型预留**：在 `packages/shared` 里提前定义 `JobPosting` 类型（职位标题、公司、地点、技能要求、来源、URL 等），后续接入不需要改画像契约
2. **Spike 验证**：花 1–2 天做个技术验证——抓 Wellfound/YC Jobs 的技术岗，跑通"抓取→去重→存储→搜索"的最小链路，确认技术路径没问题，存个笔记，P2 直接用

## 5. Chrome 扩展一键填充可行性与差异化分析

### 5.1 结论

**技术上完全可以做，而且这是比职位聚合更接近我们产品差异化的方向。** 但有个前提：**PRD 里目前把"ATS 表单自动填充"列在"非目标"里**——如果要做，需要调整这个决策。

### 5.2 技术路径

| 环节 | 方案 | 难度 |
|------|------|------|
| **扩展框架** | Chrome Manifest V3 + React/TypeScript | 低 |
| **表单识别** | 内容脚本扫描页面 input/select/textarea，按 name/id/label 匹配字段 | 中 |
| **字段映射** | 画像数据（姓名、邮箱、GitHub、技能、经历等）→ 表单字段 | 低 |
| **ATS 适配** | Workday/Greenhouse/Lever 等主流 ATS 有相对固定的字段结构，逐个适配 | 中 |
| **数据来源** | 从 JobAgent 后端拉取用户的可信画像数据，或本地存储 | 低 |
| **用户体验** | 页面右上角悬浮按钮，点一下自动填充，用户确认后提交 | 低 |

**整体评估**：2–3 周可以出 MVP 版本（支持 3–5 个主流 ATS，基础字段填充）。Simplify、LazyApply 等产品已经验证了这个模式的技术可行性和用户接受度。

### 5.3 我们的差异化优势（关键）

普通填充工具（Simplify、Jobright 扩展）填充的是**用户自己输入的简历数据**——用户编什么，它填什么，AI 幻觉简历它也照填。

**我们做的话，填充的数据来自 GitHub 验证过的可信画像**：

| 维度 | 普通填充工具 | JobAgent 扩展 |
|------|------------|--------------|
| **数据来源** | 用户手动输入或 AI 生成的简历 | GitHub 行为痕迹分析出的能力画像 |
| **可信度** | 无法验证，AI 幻觉是已知风险 | 每条技能/经历都有 evidenceRefs 可回溯 |
| **技能字段** | 用户写什么就填什么 | 来自真实仓库语言/框架/领域分析 |
| **差异化卖点** | "填得快" | "填的是招聘方能验证的真实能力" |
| **与画像的关系** | 独立工具 | 画像的"消费端"延伸——画像生成后自然可以一键投递 |

**一句话**：别人的扩展是"更快地投出你编的简历"，我们的扩展是"投出 GitHub 验证过的你"——这是本质区别。

### 5.4 风险与边界

| 风险 | 说明 | 缓解 |
|------|------|------|
| **平台改版** | ATS 表单结构变化会导致填充失效 | 聚焦头部 3–5 个 ATS，持续维护；用户可手动修正 |
| **复杂表单** | 有些公司有自定义字段、多级下拉、文件上传 | 基础字段自动填，复杂字段提示用户手动补 |
| **法律风险** | 比后台爬虫低很多——用户自己的浏览器、IP、登录态，主动触发 | 明确用户协议，不存储用户密码，只在用户授权下操作 |
| **与 PRD 决策冲突** | 目前 PRD 把"ATS 表单自动填充"列在非目标 | 需要用户确认调整决策，更新 PRD |

### 5.5 为什么这个方向比职位聚合更值得提前做

1. **与核心产品的协同更强**——画像是"我是谁"，扩展是"把我是谁投出去"，是自然延伸，不是另起炉灶
2. **差异化更明显**——可信画像数据是别人抄不走的，职位库谁都能爬
3. **用户感知价值更直接**——用户拿到画像后立刻就能用扩展投递，闭环更短
4. **技术风险更低**——比职位聚合的维护成本低，比全自动后台投递的法律风险低

### 5.6 建议排期

- **P1 阶段**（画像验证通过后）：启动 Chrome 扩展 MVP，支持 Workday/Greenhouse/Lever 三大 ATS，填充基础字段（姓名、邮箱、GitHub、技能、教育等）
- **P2**：扩展更多 ATS 平台，支持自定义字段映射，与职位匹配/一键投递打通
- **当前 MVP**：不做，但可以在 `packages/shared` 里预留可导出的画像数据结构（JSON 格式），方便后续扩展消费
